# 아키텍처 및 대용량 처리 설계

이 문서는 세 가지를 다룹니다 — **데이터 수집**, **가상 채널 + 실제 DU 시나리오**, **대용량 데이터 처리**.
근거가 되는 측정치는 모두 이 저장소에서 재현 가능합니다(`scripts/load-test.sh`).

---

## 1. 데이터 수집 (Collection)

### 1.1 문제

드라이브 테스트 도구의 본질은 **수집과 분석**입니다. 초기 구현은 분석만 있었고, 자체 생성한 데이터
외에는 아무것도 읽을 수 없었습니다.

### 1.2 설계

`POST /api/import/csv` — 스트리밍 CSV 임포트.

| 항목 | 처리 |
|---|---|
| 위치·시각 컬럼 | 이름으로 매칭 (`latitude/lat`, `longitude/lon`, `timestamp/time/ts`, `speed_kmh`, `serving_pci`) |
| KPI 컬럼 | 나머지 컬럼 중 **알려진 KPI 이름과 일치하는 것**만 적재 |
| 나머지 | `ignoredColumns`로 **반환**하여 사용자가 확인 가능 |
| 시각 형식 | ISO-8601 / epoch 초 / epoch 밀리초 |
| 위치 없는 행 | 건너뜀 |
| 메모리 | 5,000행 배치로 flush — 파일 크기가 힙이 아니라 디스크에 의해 제한됨 |

**`ignoredColumns`를 반환하는 이유**: 임포트가 "성공"했는데 아무것도 안 들어온 가장 흔한 원인이
헤더 불일치입니다. 조용히 무시하면 사용자가 알 수 없습니다.

### 1.3 검증

세션 1을 CSV로 내보낸 뒤 다시 임포트한 결과 — 1,200 샘플, 15,600 KPI 값, 13개 KPI 전부 매핑,
무시된 컬럼 0개, **RSRP 분포가 원본과 완전히 동일**(91/142/420/547).

### 1.4 아직 없는 것

- Nemo 등 **벤더 바이너리 로그 포맷** 파서 (포맷 스펙이 비공개, 리서치 §6.5 참조)
- 측정 장비로부터의 **실시간 스트리밍 수집**
- 로그 파일 자동 업로드 폴더 감시 (Nemo Analyze의 automated upload 대응)

## 2. 가상 채널 + 실제 DU 시나리오

### 2.1 시나리오

```
[에뮬레이트된 UE] --- [가상 채널] --- [실제 DU (피시험 장비)]
```

UE와 무선 채널은 소프트웨어로 만들고, DU는 실물입니다. 이 구성에서 **재현 가능한 시험**이 되려면
네 가지가 실행 기록에 함께 남아야 합니다.

### 2.2 데이터 모델

| 테이블 | 역할 | 핵심 컬럼 |
|---|---|---|
| `channel_model` | **가상 채널** | `model_type`(CDL/TDL/GEOMETRIC/**FIELD_REPLAY**), `profile`, `delay_spread_ns`, `max_doppler_hz`, `mimo_correlation` |
| `cell_config` | DU에 설정할 셀 | `band`, `bandwidth_mhz`, `scs_khz`, `duplex`, `tdd_pattern`, `mimo_layers` |
| `ue_profile` | **에뮬레이트된 UE** | `ue_count`, `traffic_profile`, `target_mbps`, `mobility_kmh` |
| `du_endpoint` | **실제 DU** | `connection_type`, `split_option`, `address` |
| `test_run` | 실행 | 위 4개 + `session_id` + `status` + `verdict` |
| `run_criterion` | 합불 기준 | `kpi_name`, `aggregate`, `operator`, `threshold`, `actual_value`, `passed` |

### 2.3 두 가지 핵심 선택

**(1) `FIELD_REPLAY` 채널 모델 타입** — VDT의 본질입니다. 통계적 프로파일(CDL/TDL)이 아니라
**실제 주행에서 기록한 채널**을 재생합니다. `source_session_id`가 원본 측정 세션을 가리킵니다.
리서치 §5.3에서 확인한 "두 갈래 재생"(무선 채널 + 시그널링 스크립트) 중 채널 축에 해당합니다.

**(2) `connection_type`에 프론트홀 포함** — 에뮬레이트된 UE가 실제 DU에 도달하는 경로는 RF만이
아닙니다.

| 값 | 의미 |
|---|---|
| `RF_CONDUCTED` | 채널 에뮬레이터를 거쳐 DU의 RF 포트에 유선 연결 |
| `RF_OTA` | 차폐실 내 공중 방사 |
| `FRONTHAUL_ECPRI` / `FRONTHAUL_ORAN_7_2X` | **RF 단을 거치지 않고 프론트홀에 디지털 주입** |

O-RAN 7.2x 분할에서는 RF 스테이지가 아예 없으므로 채널이 디지털로 적용됩니다. 이 구분이 없으면
같은 "채널 모델"이 전혀 다른 물리적 의미를 갖게 됩니다.

### 2.4 UE 측 vs 네트워크(DU) 측 지표

`kpi_definition.source`에 `UE` / `DU` / `SCANNER`를 기록합니다.

실제 DU가 피시험 대상이면 DU 자신도 카운터를 냅니다. UE 측만 보면
**"이 단말이 힘들다"와 "이 셀이 혼잡하다"를 구분할 수 없습니다.**

| DU 측 KPI | 의미 |
|---|---|
| `DU_PRB_UTILISATION` | 하향 PRB 점유율 |
| `DU_ACTIVE_UES` | RRC 연결 상태 UE 수 |
| `DU_HARQ_RETX_RATE` | HARQ 재전송 비율 |

### 2.5 합불 판정 (verdict)

`POST /api/lab/runs/{id}/evaluate` — 각 기준을 세션 측정값에 대해 평가하고 `PASS`/`FAIL`/`INCONCLUSIVE`를
기록합니다. 집계 함수는 `MEAN|MIN|MAX|P05|P50|P95`의 **폐쇄 목록**으로만 받습니다(SQL 조각에
들어가기 전에 검증).

**판정이 없으면 측정은 펌웨어 빌드를 게이팅할 수 없습니다.** 리서치 §5(기술개요 5페이지)의
*"automatic reports and verdicts"* 에 대응합니다.

### 2.6 아직 없는 것

- **실제 실행기(executor)** — 현재는 실행 기록과 판정만 있고, 장비를 실제로 구동하지는 않습니다.
  `status`/`progress_pct` 필드는 그 연결을 위해 준비된 자리입니다.
- 시그널링 스크립트(운영사별 네트워크 동작 재현) 모델링 — 리서치 §5.3의 두 번째 축
- 채널 임펄스 응답(CIR) 자체의 저장·재생

## 3. 대용량 데이터 처리

### 3.1 규모 산정 근거

Nemo Analyze 기술개요(`5992-2005EN` 7페이지)가 명시하는 수치입니다 【확인됨】.

> 측정 장비 1대가 **시간당 약 15 MB**의 데이터를 생성하며, 서버 DB에서는 압축되어 **시간당 5 MB**를
> 차지한다. 데이터 디스크는 **최소 1 TB SSD** 권장.

그리고 "**수백 시간(hundreds of hours)** 분량의 측정 데이터를 분석·관리"한다고 기술합니다.

### 3.2 초기 구현의 한계 (측정값)

8시간 1 Hz 세션 하나(28,800 샘플 / 288,000 KPI 행)에 대해:

| 엔드포인트 | 초기 | 문제 |
|---|---|---|
| `track` | **6,243,958 B** | 브라우저가 6 MB JSON을 파싱하고 28,800개 폴리라인을 그려야 함 |
| `series` | **3,953,666 B** | 동일 |
| `distribution` / `statistics` | 0.10 s | **전체 값을 Java 힙에 적재** 후 정렬 — 동시 사용자 수만큼 배가 |

`distribution`과 `statistics`가 특히 위험했습니다. 지연은 짧아 보였지만 세션당 수백만 개의
`double`을 애플리케이션 메모리로 끌어오는 구조여서, 규모와 동시성이 함께 커지면 OOM으로 갑니다.

### 3.3 변경 사항

**(1) 스키마 — `sample_kpi` 비정규화 + 파티셔닝**

```sql
sample_kpi (session_id, seq, ts, kpi_name, value)
PRIMARY KEY (session_id, seq, kpi_name)
PARTITION BY HASH (session_id)   -- 8개 파티션
```

- `session_id`/`seq`/`ts`를 직접 보유 → **모든 분석 쿼리가 단일 테이블만 읽음**(조인 제거)
- 분석은 항상 세션 단위이므로 **파티션 프루닝**이 걸림 (검증: `sample_kpi_p0`에 대한 index-only scan)
- **트레이드오프 명시**: 한 세션은 파티션을 넘나들 수 없어 세션 길이가 다르면 파티션 크기가
  불균형해집니다. 시간 기반 보존 정책이 필요한 배포라면 `RANGE(ts)`가 더 나은 키입니다
  (오래된 파티션 DROP이 O(1)).

**(2) 집계를 DB로 이동**

| 기능 | 방법 |
|---|---|
| 구간 분류 | 임계값 행에서 생성한 `CASE` 식 (사용자 입력이 SQL에 들어가지 않음) |
| 분포 | `GROUP BY <bin expr>` |
| 통계 + CDF | `percentile_cont(배열)` **단일 패스** |
| 열화 구간 | gaps-and-islands (`seq - row_number()`) |

**(3) 서버 측 데시메이션**

| 대상 | 방식 | 이유 |
|---|---|---|
| `track` | **구간 색상이 바뀌는 지점은 모두 유지** + 나머지는 stride로 솎음 | 균등 샘플링만 하면 짧은 dropout이 사라짐 — 지도가 보여줘야 할 바로 그 사건 |
| `series` | 버킷별 **최소·최대** 반환 | 평균을 내면 스파이크가 뭉개짐 |

**(4) 응답 압축** — 반복적인 JSON이라 gzip이 효과적(약 4~5배).

**(5) 지도 렌더링** — 세그먼트마다 폴리라인을 만들면 샘플당 Leaflet 레이어 + SVG 노드 + 툴팁이
생깁니다. 색상은 구간 경계를 넘을 때만 바뀌므로 **연속된 동일 색상을 하나의 폴리라인으로** 묶습니다.
8시간 경로에서 3,671개 → **81개**.

### 3.4 측정 결과

`./scripts/load-test.sh 25` — 25개 × 8시간 = **200 device-hours**

> **이 절의 수치는 KPI 정의가 13개이던 시점의 실행에서 나왔습니다 (2026-09-03 표시).**
> 카탈로그가 18개로 늘었으므로 같은 명령이 지금은 더 많은 행을 만듭니다 — `gap-analysis.md`가
> 같은 200 device-hour 실행에 대해 적은 값은 **약 1,300만 행 · 4 GB**입니다. 아래 응답
> 시간은 **9.4M 행에서 잰 값**이고 현재 값이 아닙니다. 다시 재려면 `./scripts/load-test.sh 25`
> 한 번이면 됩니다. 표를 지우지 않고 시점을 붙인 이유는, 낡은 수치보다 **낡았다고 적히지
> 않은 수치**가 나쁘기 때문입니다.

| 항목 | 값 |
|---|---|
| 세션 | 28 |
| 샘플 | 723,300 |
| KPI 행 | **9,418,500** (KPI 정의 13개 시점) |
| `sample_kpi` 파티션 합계 | 2,800 MB |
| DB 전체 | 1,873 MB |

이 상태에서 8시간 세션 하나에 대한 응답:

| 엔드포인트 | 시간 | gzip 크기 |
|---|---|---|
| `distribution` | 41 ms | 306 B |
| `statistics` | 31 ms | 724 B |
| `track` (maxPoints=4000) | 90 ms | 172 KB |
| `series` (2 KPI) | 84 ms | 68 KB |
| `degradations` | 66 ms | 814 B |
| `bins` (150 m) | 45 ms | 6.9 KB |
| `coverage-issues` | 75 ms | 1.4 KB |

UI: **세션 선택 → 경로 렌더 완료 202 ms** (81 폴리라인, 28,800 샘플에서 3,671점으로 데시메이션,
범례는 28,800개 전부를 분류).

### 3.5 개선 이력 중 기록해둘 것

| 발견 | 원인 | 조치 |
|---|---|---|
| `statistics` 0.10 s → **2.8 s로 악화** | CDF를 101회의 개별 `percentile_cont`로 계산 → 컬럼을 101번 정렬 | 배열 형태 단일 패스로 변경 → **0.086 s** |
| 지도 렌더 "32초" | **측정 오류.** 프로브가 `networkidle`을 기다렸고, 샌드박스에서 차단된 지도 타일 요청이 그만큼 늦게 실패 | 폴리라인 그룹화는 유지(상호작용·메모리에 유효), 수치는 정정 |

### 3.6 더 큰 규모에서 필요할 것

현재 구조는 수백 시간 규모까지 검증했습니다. 그 이상에서는:

| 규모 | 필요한 조치 |
|---|---|
| 수천 시간, 보존 정책 필요 | `RANGE(ts)` 파티셔닝으로 전환 — 오래된 파티션 DROP |
| 다중 세션 집계가 느려질 때 | 사전집계 테이블 재도입. **지금은 없습니다** — 아래 참조 |
| 초당 수천 샘플 이상 | TimescaleDB 하이퍼테이블 또는 컬럼 지향(ClickHouse) 검토 |
| 지도에서 수십만 점 | 벡터 타일 사전 생성 + PostGIS |

**정정 (2026-09-03).** 이 표는 오랫동안 "`kpi_rollup` 스키마는 이미 있음"이라고 적어
두었는데, 그 테이블은 **V3에서 삭제됐습니다**(`V3__drop_unused_rollup.sql`). 쓰이지 않는
스키마가 남아 있는 것보다 나쁜 것은 **없어진 스키마를 있다고 적어 둔 문서**입니다 — 다음
사람이 그것을 계획의 기반으로 삼기 때문입니다.

지금 다중 세션 집계를 하는 것은 **`CohortService`의 풀링 질의**입니다(2026-09-03, P4-3).
사전집계 없이 `sample_kpi`를 직접 읽고, 그래야 하는 이유가 있습니다: 그룹의 **백분위**는
세션별 부분합에서 복원되지 않으므로, 세션별 요약을 미리 만들어 두어도 CDF는 여전히 원시
행에서 다시 읽어야 합니다. 사전집계는 평균과 개수만 빠르게 하고 화면에 필요한 나머지 절반은
그대로 남깁니다. 그래서 지금 규모에서는 값이 없고, **필요해지기 전에 만드는 것은 근거 없는
최적화**입니다. 필요해지는 조건은 명확합니다 — 코호트 하나가 200 주행 상한
(`SessionSet.MAX_MEMBERS`)에 닿고 응답이 예산을 넘길 때입니다.
