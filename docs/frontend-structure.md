# UX가 바뀔 때 코드가 따라올 수 있는가 — 워크북 내보내기가 실측한 것

*2026-09-05. 이 문서는 의견이 아니라 **한 기능이 실제로 치른 비용의 기록**입니다.*

워크북 내보내기를 만들면서 "지금 구조가 UX 변화를 흡수할 만큼 모듈화돼 있는가"를
같이 물었습니다. 답은 **부분적으로 그렇다**이고, 어느 부분인지가 이 문서의 전부입니다.
추상적인 평가 대신 **이 기능이 손대야 했던 것과 손댈 필요가 없었던 것**을 셉니다.

## 1. 결론

| | 무엇이 | 근거 |
|---|---|---|
| **준비돼 있었다** | 서버의 **결과·출처·포맷** 계층, 프론트의 **뷰 규칙 모듈**, **검사 하네스** | 한 줄도 고치지 않고 그대로 쓰였습니다 |
| **준비돼 있지 않았다** | **차트 기하**가 컴포넌트 안에 있었습니다 | 내보내기 첫 줄을 쓰기 전에 **모듈 둘을 먼저 뜯어내야** 했습니다 |
| **여전히 아니다** | 나머지 차트 여섯, `App.tsx`, 그리고 페이지 개념의 부재 | 아래 §4 |

즉 **구조는 이번 변화를 흡수하지 못했고, 흡수할 수 있게 만든 다음에야 기능이 들어갔습니다.**
그 순서가 비용의 전부입니다. 새로 쓴 1,763줄을 갈라 보면:

| | 줄 | 무엇 |
|---|---|---|
| **기능** | 770 | `view/doc/*` 여섯 + 컨트롤 하나 |
| **추출** | 399 | `panegeom.ts` 223 + `routeruns.ts` 176 — *기능이 아니라 기능을 가능하게 한 것* |
| **검사** | 483 | verify-ui +226 · verify-scenarios +95 · api-surface +54 · 주입 +108 |
| **컴포넌트 축소** | −182 | `RouteMap` −124 · `MultiSeriesChart` 97줄 → 55줄 |

기능보다 **추출 + 검사(882줄)가 더 큽니다.** 그 비율이 이 질문에 대한 가장 정직한 답입니다.

## 2. 준비돼 있던 것 — 한 줄도 고치지 않았습니다

이번 라운드가 **읽기만 하고 고치지 않은** 모듈들입니다. 재사용성의 정의가 이것입니다.

| 모듈 | 이번에 한 일 | 왜 그냥 됐나 |
|---|---|---|
| `view/paint.ts` | 트레이스 색(`seriesColor`), 경로 색(`paint`), PCI 색(`buildPciColors`) | 이미 **컴포넌트 밖**에 있었습니다 |
| `view/maplayers.ts` | 문서의 지도 캡션(`describeLayers`) | "이 그림에 뭐가 있나"의 유일한 답이 이미 하나였습니다 |
| `GET /global-filter/describe` | 문서가 조건을 **서버 문장 그대로** 인쇄 | 그 엔드포인트가 존재하는 이유가 정확히 이것이었습니다 |
| `GlobalFilter.coverage()` | 새 엔드포인트가 없으니 목록 변화 0 | — |
| `ExportScope`의 **교리** | 문서의 `DocScope`가 그대로 따름(파일에 한 번, **페인마다** 한 번) | 규칙이 코드가 아니라 **문장으로** 적혀 있어 다른 매체로 옮길 수 있었습니다 |
| `verify-ui` · `verify-scenarios` · `api-surface` · `defects.mjs` | 검사 14 + 시나리오 4 + 정적 규칙 3 + 주입 11을 **기존 관용구 그대로** 추가 | — |

> **이 목록이 말하는 것.** 서버 쪽은 이번 UX 변화에 **아무 영향도 받지 않았습니다.**
> 마이그레이션 0, 새 엔드포인트 0, Java 변경은 결함 수정 한 곳뿐입니다. 분석 계층이
> "질문을 받아 답하는" 모양이라 화면이 어떻게 바뀌든 상관이 없었기 때문입니다.

## 3. 준비돼 있지 않던 것 — 기능보다 먼저 낸 비용

내보내기가 **불가능했던** 이유는 하나입니다. **페인의 기하가 그림을 그리는 함수 안에만
있었습니다.** `MultiSeriesChart`는 JSX를 반환하는 함수였고, 정규화·경로 문자열·눈금·범례
숫자가 전부 그 반환문 안에서 계산됐습니다. `RouteMap`은 더 심해서, 런(run) 경계와 브레이크
분류가 **Leaflet에 넘기는 `useEffect` 안**에 있었습니다.

그래서 선택지는 둘뿐이었습니다.

1. **내보내기가 다시 그린다** — 두 번째 플로터. 이 저장소가 `RouteContinuity`,
   `event_type`, `AggregationBasis`, `Csv`에서 네 번 배운 그 실수이고, 그림에서는 최악입니다:
   **두 그림 다 맞는 주행의 차트처럼 보입니다.**
2. **기하를 꺼낸다** — `view/geom/panegeom.ts`, `view/geom/routeruns.ts`.

2번을 골랐고, 그 결과가 이 라운드의 진짜 산출물입니다.

```
그 전:  MultiSeriesChart(데이터) -> JSX            RouteMap useEffect(track) -> Leaflet 객체
지금:   composeChartPane(데이터) -> 기하 객체       composeRuns(track) -> 런·브레이크·프레임
        └ MultiSeriesChart가 그림                   └ RouteMap이 Leaflet에 넘김
        └ workbookdoc가 SVG 텍스트로 씀             └ project.ts가 문서용으로 투영
```

**얻은 것은 코드 정리가 아니라 검사 가능성입니다.** 기하가 순수 모듈이 되자 검사기가
Node에서 그것을 `import`해서 **브라우저가 그린 `d` 문자열과 문자 단위로 비교**할 수
있게 됐습니다. "내보낸 것이 화면과 같은 계산"이 약속이 아니라 **단언**이 된 것이 이번 설계의
전부이고, 그 전 구조에서는 어떤 검사로도 그 문장을 세울 수 없었습니다.

### 이 추출이 드러낸 결함 넷 — 전부 이번 변경보다 오래된 것

계산을 꺼내 놓자 **읽을 수 있게 됐고**, 읽자마자 보였습니다.

| 결함 | 왜 안 보였나 |
|---|---|
| 페인의 빈 곳을 클릭하면 예외 (`ownerSVGElement`가 null) | 아무 검사도 페인을 클릭한 적이 없었습니다 |
| 클릭→커서 변환이 좌측 패드를 안 뺌 → 주행의 **약 4.6%** 어긋남 | 정변환과 역변환이 **다른 함수**에 있었습니다. `TimeSeriesChart`는 줄곧 옳았습니다 |
| 구성 페인만 커서 **이후** 표본을 읽음(나머지는 이전) | 두 화면을 같은 커서로 나란히 놓고 숫자를 비교한 적이 없었습니다 |
| 모든 표본 CSV·GeoJSON 이름이 `...-1-4-2-.csv` | 파일 **이름**을 읽는 코드가 없었습니다. 브라우저가 만든 이름과 대조하자 나왔습니다 |

> 세 번째와 네 번째는 §1.5의 오래된 교훈을 다시 확인해 줍니다 — **두 값을 나란히 놓기
> 전까지는 어긋남이 어긋남으로 보이지 않습니다.**

## 4. 여전히 준비돼 있지 않은 것

이번에 **고치지 않은** 것들입니다. 고칠 수 있었지만 이 기능이 요구하지 않았고,
요구하지 않는 리팩터를 끼워 넣으면 회귀의 원인을 가릴 뿐입니다.

| 항목 | 크기 | 무엇이 걸리나 |
|---|---|---|
| **차트 여섯 개의 자기 축** | 중 | `CdfOverlay.tsx:55-56`과 `StatisticsPanel.tsx:53-54`는 **바이트까지 같은 두 줄**이고, 경로 빌더도 입력만 다릅니다. `TimeSeriesChart`·`CohortStrip`·`CellBarChart`·`DistanceProfile`이 각자 `PAD`와 선형 사상을 갖습니다. **이 중 무엇도 내보낼 수 없습니다** — 워크북 페인만 할 수 있는 이유가 그것입니다 |
| **`App.tsx` 1,634줄** | 큼 | 세션·KPI·커서·범위·필터·탭·지도 내용물이 한 컴포넌트의 상태입니다. 새 화면은 여기에 줄을 더하는 방식으로만 붙습니다 |
| **페이지 개념 부재** | 중 | 레퍼런스의 워크북은 **페이지**를 갖고 페이지마다 그림을 냅니다(p220·p223). 우리 스키마엔 페인만 있습니다. `workbookdoc.ts`가 `pages: [{name, panes}]`를 이미 받고 합성 페이지 하나를 받고 있어서, V15가 `workbook_page`를 넣는 날 문서 쪽은 **한 줄**만 바뀝니다. 비용은 전부 편집기(`draft.panes`를 읽는 자리 열 곳)에 있습니다 |
| **`workbook_pane.title`이 쓰이지 않음** | 매우 작음 | 컬럼도 있고 저장·조회도 되는데 **제목을 바꾸는 컨트롤이 없습니다**. 문서는 화면과 같은 대체값을 씁니다 |
| **`RouteMap`의 나머지** | 중 | 경로는 꺼냈지만 셀 마커·이벤트·빈·푸트프린트·서빙 선은 여전히 `useEffect` 안입니다. 문서의 지도가 경로만 그리는 이유가 이것입니다 |

### 그리고 증명 라운드가 드러낸 결함 넷 — 이번에는 **검사** 쪽

결함 열하나를 하나씩 주입해 새 검사 열넷이 실제로 빨개지는지 봤습니다. 열하나는 전부
겨눈 검사를 빨갛게 만들었고, **그 과정에서 검사 자체의 결함이 넷 나왔습니다** — 예외를 던져
중단되면서 `0 failing`으로 보고하던 검사, `<figcaption>`과 그림의 `<desc>`를 구별 못 하던 검사,
서버 문장과 **글자까지 같은 것**을 만들어 아무것도 증명하지 못한 주입, 그리고 직전 실행이
남긴 워크북이 다음 실행을 빨갛게 만들던 오염. 상세는
[`ui-testing/README.md` §1.5.21](ui-testing/README.md).

이것이 §3의 결함 넷과 같은 이야기입니다. **꺼내 놓아야 읽을 수 있고, 읽어야 틀린 것이
보입니다** — 코드에서든 검사에서든.

## 5. 규칙을 두 언어에 쓴 자리 하나 — 숨기지 않고 묶었습니다

문서 파일 이름의 **슬러그 규칙**은 `AnalyticsController.fileName`(Java)에 있고, 브라우저가
파일을 만들므로 `view/doc/naming.ts`(TypeScript)에도 있습니다. 이 저장소가 보통 거부하는
모양입니다.

지우는 대신 **검사로 묶었습니다**: 같은 측정의 CSV(서버가 이름 지음)와 워크북 문서(여기서
이름 지음)를 받아 **측정 슬러그가 문자까지 같은지** 단언합니다. 둘이 갈라지면 빨개집니다 —
공유된 규칙이 갖는 성질이고 복사된 규칙은 보통 갖지 못하는 성질입니다.

그리고 이 검사가 처음 돌자마자 **서버 쪽 이름의 하이픈 결함**이 나왔습니다(§3의 넷째).

## 6. 그래서, 유연한가

**질문을 셋으로 나눠야 답이 정확해집니다.**

1. **서버 로직이 UX를 따라올 수 있나** — **예.** 이번 UX 변화가 백엔드에 요구한 것은 0입니다.
   분석이 "질문에 답하는" 모양이고 결과·출처·포맷이 각각 한 곳에 있어서입니다.
2. **프론트의 *규칙*이 따라올 수 있나** — **예, 이미 꺼내 놓은 것에 한해.** `view/`에 있던
   것은 전부 그대로 쓰였고, 컴포넌트 안에 있던 것은 하나도 쓰이지 못했습니다.
3. **프론트의 *그림*이 따라올 수 있나** — **아직 절반.** 워크북 페인 둘은 이제 가능하고,
   나머지 차트 여섯은 불가능합니다. 다음에 "이 화면도 내보내 달라"가 오면 **그 화면의
   기하를 먼저 꺼내는** 같은 비용을 다시 냅니다. 다만 두 번째부터는 `panegeom.ts`라는
   갈 곳이 있어서 첫 번째보다 쌉니다.

> **한 문장으로.** 이 코드베이스는 *규칙*에 대해서는 잘 모듈화돼 있고 *그림*에 대해서는
> 그렇지 않았습니다. 이번 라운드가 그림 쪽에서 두 조각을 꺼냈고, 꺼내자마자 오래된 결함
> 넷이 보였습니다 — 그것이 모듈화의 값어치가 실제로 회수되는 방식입니다.
