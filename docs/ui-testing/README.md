# UI 검증 기법 리서치 — 실측 기반

> Virtual Drive Test 제품 요구사항과 **분리된** 별도 주제입니다.
> 다만 실험 대상은 같은 저장소를 씁니다. 이미 30개 브라우저 체크와 실제 백엔드/프론트엔드 계약이
> 있어서, 가설이 아니라 **측정**이 가능하기 때문입니다.

세 질문을 다룹니다.

1. 로직은 추가됐는데 뷰가 안 따라오는 상황을, 토큰을 아끼면서 어떻게 잡을 것인가
2. AI 개발에서 프론트엔드 오동작을 어떻게 자동으로 검출하고 수정하게 만들 것인가
3. UX-driven development의 best practice는 무엇이고, 실제로 유효한가

리서치와 동시에 이 저장소에 적용했고, 적용 결과도 함께 적었습니다.

---

## 0. 방법과 정직성 경계

### 0.1 무엇이 측정값이고 무엇이 추정인가

| 값 | 성격 |
|---|---|
| 신호별 **바이트 수** | **정확한 측정** |
| 이미지 **visual token** | **정확한 계산.** 문서의 패치 공식을 구현하고 문서 예시 10개와 전부 대조 |
| 텍스트 **토큰 수** | **추정** (문자수/4). 이 환경에 API 자격증명이 없어 `messages.count_tokens` 사용 불가 |
| 결함 검출 여부 | **정확한 측정** (결함을 실제로 심고 실행) |

텍스트 토큰이 추정인 점은 결론을 훼손하지 않습니다. 비교의 근거는 신호 간 **비율**이고,
그 비율은 바이트로 안정적으로 드러납니다. 추정치를 측정치처럼 제시하지 않는 것이 중요합니다.

### 0.2 이미지 토큰 공식 — 기억에 의존하지 말 것

처음 코드 주석에 `(width × height) / 750`, 상한 1568px라고 적었습니다. **틀렸습니다.**
현재 문서화된 규칙은 패치 기반입니다.

> "Claude views images in patches instead of pixels. Each patch is a 28×28-pixel block of the
> image, referred to as a visual token. An image, therefore, costs `⌈width / 28⌉ × ⌈height / 28⌉`
> visual tokens."

| 티어 | 대상 | 최대 장변 | 최대 visual token |
|---|---|---|---|
| High-resolution | Claude 4.7 이후 | 2576 px | 4784 |
| Standard | 그 외 | 1568 px | 1568 |

출처: <https://platform.claude.com/docs/en/build-with-claude/vision>

구현(`tools/uxtest/signals.mjs`의 `imageTokens()`)은 문서 예시 표 10개와 **축소 후 해상도까지 전부
일치**합니다. 1080p 스크린샷 하나가 standard 1,560 / high-res 2,691 토큰입니다.

## 1. Q1 — 로직은 추가됐는데 뷰가 없다

### 1.1 신호별 비용 (이 앱, 1680×1000 뷰포트)

| 신호 | 바이트 | 토큰 | 스크린샷 대비 |
|---|---|---|---|
| S1 런타임 오류 (console/pageerror/requestfailed) | 151 | ~38 | **57× 저렴** |
| S2 DOM innerText | 3,232 | ~805 | 2.7× 저렴 |
| S3 ARIA 스냅샷 (기본, 전체 깊이) | 8,746 | ~2,184 | **1.0× — 스크린샷과 동일** |
| S4 구조 다이제스트 (직접 작성한 투영) | 853 | ~212 | **10× 저렴** |
| S5 전체 스크린샷 | 211,850 | **2,160 (정확)** | 기준 |
| S6 단일 실패 단언 결과 | 73 | ~18 | **120× 저렴** |

**의외의 결과**: ARIA 스냅샷이 스크린샷보다 싸지 않습니다. 이 앱은 데이터 테이블이 많고 접근성
트리가 셀을 전부 열거하기 때문입니다.

> Playwright MCP 문서는 스냅샷 ~200–400 토큰, 스크린샷 ~3,000–5,000 토큰이라고 적고 있으나,
> 사실 검증 결과 **벤더의 자체 근사치이며 측정 벤치마크가 아닙니다.** 그리고 데이터 밀도가 높은
> 화면에서는 제 실측(2,184 vs 2,160)과 어긋납니다. 화면 성격에 따라 달라지는 값입니다.

### 1.2 ARIA 스냅샷은 `depth`로 통제한다

`locator.ariaSnapshot()`에는 비용을 직접 조절하는 옵션이 있습니다 — `depth`(v1.59),
`mode: 'ai'|'default'`(v1.59), `boxes`(v1.60). 실측했습니다.

| depth | default 모드 | `mode:'ai'` |
|---|---|---|
| 1 | 2,637 B | **85 B** |
| 2 | 4,839 B | 641 B |
| 3 | 8,768 B | 1,488 B |
| 5 | 8,768 B | 5,994 B |
| 제한 없음 | 8,768 B | 23,612 B |

두 가지를 읽을 수 있습니다.

- **`mode:'ai'`는 전체 깊이에서 2.7배 더 비쌉니다.** 상호작용용 `[ref=eN]`가 붙은 generic 컨테이너를
  전부 포함하기 때문입니다. 얕게 자를 때만 이득입니다.
- **default 모드는 depth 3에서 포화합니다.** generic 래퍼를 이미 생략하므로 트리가 얕습니다.

"구조가 살아 있는가"만 확인할 거라면 **default 모드 depth 1–2(2.6–4.8 KB)** 가 합리적입니다.

> 제 첫 측정에서는 `depth:3`과 `depth:5`가 같은 크기로 나와 "depth는 효과가 없다"고 결론지을 뻔했습니다.
> 두 값 모두 포화점 이후였을 뿐입니다. **한 구간만 보고 옵션이 무효라고 판단하면 안 됩니다.**

> **API 주의**: `page.accessibility.snapshot()`은 **Playwright 1.57에서 제거**되었습니다
> (3년간 deprecated 후). 1.62.1에서 `undefined`이며, 기억하던 이 API를 그대로 쓰면 런타임에 터집니다 —
> 실제로 이 실험이 그렇게 터지면서 알게 됐습니다.

### 1.3 비용만 보면 안 된다 — 결함 주입 실험

싼 신호가 아무것도 못 잡으면 무의미합니다. **의도적으로 결함을 심고** 각 검출기를 측정했습니다.

**노이즈 바닥 먼저.** 무결점 상태에서 동일 프로브를 두 번 돌려 비교한 결과 5개 신호 전부
**완전히 동일**했습니다. 이 앱은 결정론적으로 렌더링되므로 diff 기반 검출이 성립합니다.
이 확인을 건너뛰면 diff 검출기는 거짓 양성 기계가 됩니다.

**검출 매트릭스** (숫자는 피드백 바이트, — 는 해당 없음)

| 결함 | 성격 | typecheck | 런타임오류 | domText | ARIA | 다이제스트 | 라우트 다이제스트 | 단언 스위트 |
|---|---|---|---|---|---|---|---|---|
| D1 KPI가 트리에 안 나옴 | 로직O 뷰X | miss | miss | **43** | 715 | 62 | — | 35 |
| D2 범례에서 건수·비율 누락 | 로직O 뷰X | miss | miss | **57** | 251 | 187 | — | 74 ※ |
| D3 워크북 탭이 빈 화면 | 로직O 뷰X | miss | miss | miss | miss | miss | **140** | miss |
| D4 시간 커서 동기화 끊김 | 상호작용 | miss | miss | miss | miss | miss | miss | **123** |
| D5 임계 색상 클래스 누락 | 시각만 | miss | miss | miss | miss | **33** | — | miss |

### 1.4 매트릭스에서 나오는 결론

**모든 것을 잡는 단일 기법은 없습니다.** 여섯 결함이 각각 다른 검출기에 걸렸습니다.

- **타입 체크는 이 결함군을 하나도 못 잡습니다.** 타입은 멀쩡하기 때문입니다. "TypeScript를 쓰니까
  괜찮다"는 이 문제에 대한 답이 아닙니다.
- **가장 싼 텍스트 신호(domText)가 "로직O 뷰X"를 43–57바이트에 잡습니다.** 스크린샷의 1/50 비용.
- **CSS 클래스만 사라진 회귀(D5)는 직접 만든 구조 다이제스트만 잡았습니다** — 33바이트로.
  값은 전부 정상이고 임계 초과 표시만 안 되는 상태라, 텍스트에는 아무 변화가 없습니다.
- **상호작용 파손(D4)은 오직 행위 단언만 잡습니다.** 어떤 정적 스냅샷도 "커서를 옮겼을 때 값이
  따라오는가"를 볼 수 없습니다. 스냅샷은 한 시점의 사진이지 인과가 아닙니다.
- **라우트 커버리지가 신호 선택보다 중요할 때가 있습니다(D3).** 처음엔 6개 검출기 전부 놓쳤는데,
  이유는 신호가 약해서가 아니라 **프로브가 그 화면에 가지 않아서**였습니다. 워크북 탭을 순회하는
  신호를 추가하자 140바이트에 잡혔습니다.

**권고 조합** (비용 오름차순, 누적):

1. 런타임 오류 싱크 (~150 B) — 크래시 계열
2. 라우트 순회 구조 다이제스트 (~1 KB) — 뷰 누락, 죽은 화면, 클래스 소실
3. 행위 단언 스위트 — 상호작용
4. 스크린샷은 **사람이 볼 때만**, 또는 위 셋이 모두 통과했는데도 이상할 때만

### 1.5 실험이 내 테스트의 허점을 드러냈다

D2에서 제 30개 단언 스위트가 **놓쳤습니다.** 단언이 이랬습니다.

```js
check('색상 범례에 건수·비율 포함', legendRows >= 5 && /%/.test(legendText))
```

범례 **헤더**에 `%` 글자가 있어서, 데이터 행의 건수·비율 칸을 전부 지워도 통과했습니다.
"페이지 어딘가에 %가 있다"를 검사하고 있었지 "각 구간에 수치가 있다"를 검사하지 않았습니다.

수정 후:

```js
const legendStats = await page.locator('.dock.right .legend-row')
  .filter({ has: page.locator('.swatch') })
  .evaluateAll((rows) => rows.map((r) => ({
    count: r.querySelector('.count')?.textContent?.trim() ?? '',
    pct: r.querySelector('.pct')?.textContent?.trim() ?? '',
  })).filter((x) => /^\d+$/.test(x.count) && /^\d+(\.\d+)?%$/.test(x.pct)))
check('색상 범례에 건수·비율 포함', legendRows >= 5 && legendStats.length >= 4)
```

정상 상태에서 `5 with count+pct`로 통과, D2 주입 시 `1 with count+pct`로 **실패**합니다.

> 교훈: **단언이 실제로 실패하는지 확인하지 않은 단언은 통과하는지도 모르는 단언입니다.**
> 결함 주입은 테스트 자체를 테스트하는 유일한 방법입니다. 30개 중 최소 1개가 무의미했습니다.

### 1.5.1 같은 실수의 두 번째 얼굴 — 파생값을 재고 원본을 안 재기 (2026-09-01)

§1.5는 **엉뚱한 것을 재는** 단언이었습니다. 이건 다릅니다. 겨냥은 정확한데 **원본이 아니라
그 원본과 무관하게 계산되는 파생값**을 읽습니다. 겉보기에는 훨씬 그럴듯해서 더 오래 삽니다.

문제 드릴다운의 "맥락 창" 검사가 이랬습니다.

```js
const ctxSpan = await page.locator('.case-context .ctx-span').innerText()  // "showing 0–111"
const windowWidth = Number(shown[2]) - Number(shown[1])
step('the context view is a window, not the whole drive', windowWidth < total / 2)
```

캡션은 `CONTEXT_PAD` **산술**입니다. 차트에 창을 넘겼든 안 넘겼든 같은 문장을 인쇄합니다.
창 prop을 `null`로 만들자 차트는 주행 전체를 그렸고, 검사는 `111 samples of 1174`로
**통과**했습니다. 캡션이 차트를 대신해서 옳은 말을 해 준 것입니다.

수정은 차트가 **실제로 그린 것**을 재는 것입니다. x축 눈금 라벨은 그려진 점에서 뽑은
시각이므로 차트가 무시하는 캡션과 일치할 수 없습니다.

```js
// textContent, not innerText: innerText는 SVG <text>에서 undefined입니다
const clocks = (await page.locator('.case-context svg text').allTextContents())
  .filter((t) => /^\d\d:\d\d:\d\d$/.test(t))
  .map((t) => t.split(':').reduce((a, n) => a * 60 + Number(n), 0))
const drawnSpan = Math.max(...clocks) - Math.min(...clocks)
```

주입 시 `chart spans 1199s of a 1174-sample drive`로 **실패**합니다.

> 교훈: **무엇을 재는지보다 그 값이 어디서 오는지를 물으십시오.** 검사 대상과 같은 입력에서
> 독립적으로 계산되는 값은 대상이 고장 나도 옳은 답을 계속 인쇄합니다.
> 같은 세션의 다른 사례: 세 화면이 거리 규칙을 공유하자 **규칙이 틀렸는데도 서로 동의**해서
> "화면 간 일치" 검사가 통과했습니다. 잡은 것은 독립 불변식(같은 경로 두 세션은 같은 길이)뿐이었습니다.
> 두 사례 모두 **단언끼리 서로를 통과시켜 준** 경우입니다.

### 1.5.2 검사기가 자기 트립와이어를 3분의 1 지점에서 껐다 (2026-09-01)

`verify-ui.mjs`의 콘솔 오류 검사는 이렇게 생겼습니다.

```js
const appErrors = errors.filter(...)     // 234행
…                                        // 533행 분량의 검사
check('앱 코드 콘솔 오류 없음', appErrors.length === 0)   // 767행
```

`errors`는 `page.on('pageerror')`가 밀어 넣는 **살아 있는 배열**이지만, `filter`는 호출
시점의 내용을 **복사**합니다. 234행 이후에 발생한 콘솔 오류는 767행의 단언에 **도달하지
않습니다.** 775행짜리 실행에서 트립와이어가 무장된 구간은 앞의 3분의 1뿐이었습니다.

`filter`를 소비 지점 바로 앞으로 옮기고, 같은 빌드에 늦은 콘솔 오류를 하나 심어 두 배치를
비교했습니다.

| `filter` 위치 | 결과 |
|---|---|
| 소비 지점(770행) | **FAIL** — 잡습니다 |
| 533행 앞(234행) | PASS — 못 봅니다 |

> 교훈: **검사기 코드도 검사 대상입니다.** 그리고 이것 역시 §1.5.1과 같은 병입니다 —
> 단언이 읽은 것은 사건의 기록이 아니라 **사건 기록의 옛 사본**이었습니다.

### 1.5.3 "포트가 응답한다"는 "그 컨테이너가 떠 있다"가 아니다 (2026-09-01)

주입 하네스의 준비 대기가 이랬습니다.

```js
try { sh('curl -sf http://127.0.0.1:4173 > /dev/null'); return } catch { sh('sleep 3') }
```

이전 세션이 남긴 `vite preview --port 4173` 프로세스가 **두 시간 전 `frontend/dist`**를
같은 포트로 계속 서빙하고 있었습니다. 컨테이너는 `address already in use`로 뜨지 못했는데,
`curl`은 200을 받으므로 하네스는 "준비됨"으로 판단했습니다. **검증 실행 한 회분이 통째로
엉뚱한 빌드를 측정했습니다.**

수정은 응답의 **출처**를 확인하는 것입니다. 컨테이너는 nginx이고, `vite preview`는 이
헤더를 보내지 않습니다.

```js
const h = sh("curl -sI --noproxy '*' http://127.0.0.1:4173")
if (/^server:\s*nginx/im.test(h)) return
throw new Error('port 4173 answered, but not from the nginx container')
```

> 교훈: **응답이 있다는 사실은 무엇이 응답했는지 말해 주지 않습니다.** §1.5.1의 캡션,
> §1.5.2의 배열 사본에 이어 세 번째로 같은 모양입니다 — 대상과 **독립적으로 참일 수 있는
> 신호**를 대상의 증거로 읽었습니다.
>
> 영향 범위는 시각으로 확정했습니다. 항목 ②의 검증(07:36–07:43)은 이 프로세스가 시작된
> 09:40보다 두 시간 앞서므로 컨테이너를 측정한 것이 맞고, 그 사이에 낀 실행 한 회만
> 무효 처리하고 다시 돌렸습니다.

### 1.5.4 중복이 "동작함"과 "일하고 있음"을 구별 불가능하게 만든다 (2026-09-01)

Esc가 모달을 닫는지 확인하는 검사를 넣고, 증명하려고 `LegendEditor`의 등록을 껐습니다.
**검사는 통과했습니다.** 모달은 여전히 닫혔습니다.

`useDismissable`이 **두 곳**에 등록되어 있었기 때문입니다 — `App`이 `editingScale`을
소유하므로 이미 등록했고, 컴포넌트가 한 번 더 했습니다. 어느 쪽을 꺼도 나머지가 닫습니다.
둘 다 "동작한다"고 보이지만 **어느 것도 자기가 일하고 있음을 증명할 수 없습니다.**

App 쪽만 남기자 같은 주입이 `modal 1 -> 1`로 실패합니다.

> 교훈: **결함 주입은 기능뿐 아니라 중복도 드러냅니다.** 무엇을 꺼도 아무 일이 없다면
> 그것은 견고함이 아니라 **관측 불가능성**입니다.

### 1.5.5 지도 뷰포트의 증인으로 경로 bbox를 쓰면 안 된다 (2026-09-01)

"파라미터를 바꿔도 지도가 그대로인가"를 재려면 뷰포트를 재야 하는데, Leaflet에서 **그려진
경로는 뷰포트의 충실한 증인이 아닙니다.**

`Polyline._clipPoints`가 렌더러 경계 밖 폴리라인을 잘라내고, 완전히 벗어난 것은
`pointsToPath`가 리터럴 `d="M0 0"`으로 씁니다. 게다가 리마운트하면 새 렌더러에 대해 다시
자릅니다. 조사 에이전트가 측정한 값: 뷰포트가 **바이트 단위로 동일한데** bbox가
`{x:-99,w:1075}`에서 `{x:0,w:976}`으로 — 2 px 허용치에 99 px 어긋납니다.

두 가지로 피했습니다.

1. **확대가 아니라 축소로** 뷰포트를 바꿉니다. 축소하면 경로 전체가 패널 안에 남아
   아무것도 잘리지 않으므로 bbox가 다시 충실해집니다.
2. `d === 'M0 0'` 인 path를 **거른 뒤** 합집합을 냅니다. 거르지 않으면 완전히 잘린 상태
   두 개를 비교하면서 "같다"고 통과합니다.

> 교훈: **렌더러가 그리는 것과 렌더러가 보는 것은 다릅니다.** §1.5.1의 캡션과 같은
> 자리에 있는 실수입니다 — 대상(뷰포트)이 아니라 대상의 **표현**(잘린 경로)을 쟀습니다.

### 1.5.6 그릇을 재고 내용물을 안 쟀다 (2026-09-01)

"지운 세션을 가리키는 링크가 그 사실을 알리는가"를 이렇게 쟀습니다.

```js
step('a link to a deleted measurement says so',
  (await dead.locator('.view-notice').count()) === 1)
```

보고 코드를 통째로 죽이는 주입을 넣었는데 **검사가 통과했습니다.** 보낸 사람의 seq를
버리는 일은 **세션 변경 리셋도** 하기 때문에 동작은 여전히 옳았고, 알림은 세션에 대한
줄 하나만 남은 채로 **여전히 존재**했습니다.

알림이 **무엇을 적는지** 재도록 바꾸자 실패합니다.

```js
&& /s=99999/.test(deadNotice) && /seq=612/.test(deadNotice) && /r=300-800/.test(deadNotice)
```

> 교훈: **존재를 재지 말고 내용을 재십시오.** §1.5.1(캡션) · §1.5.2(배열 사본) ·
> §1.5.3(포트 응답) · §1.5.5(잘린 경로)에 이어 다섯 번째로 같은 모양입니다 — 대상과
> **독립적으로 참일 수 있는 신호**를 대상의 증거로 읽었습니다. 이 저장소에서 지금까지
> 나온 검사 결함은 **전부** 이 한 가지였습니다.

### 1.5.7 주입이 컴파일되지 않으면 주입이 아니다 (2026-09-02)

P0/P1 여섯 건을 고치고 새 검사 여섯 개를 넣은 뒤, 각각에 결함을 주입해 실패를 확인했습니다.
**여섯 번 중 네 번, 첫 주입이 잘못됐습니다.** 검사가 아니라 주입이 틀린 것인데, 넷 다
**"통과"로 보였습니다.**

| 주입 | 왜 통과했나 |
|---|---|
| 격리 게이트 제거 | `tabIsolates`가 미사용이 되어 **`npm run build`가 실패**했고, 컨테이너가 **이전 번들을 계속** 서빙했습니다. 검사는 고쳐진 코드를 상대로 통과한 것입니다 |
| `paintBar` 무력화 | 파라미터 둘이 미사용이 되어 컴파일 거부 |
| 지도 페인이 레이어 무시 | `tracks`에 항목이 **하나뿐**이라 `Object.values(tracks)[0]`가 `tracks[visible[0].kpiName]`와 **같은 값**이었습니다 — 무의미한 치환 |
| 지도 체크 배타성 제거 | 배타성이 **두 핸들러**(체크박스와 셀렉트)에 있는데 하나만 지웠고, 검사는 셀렉트로 조작합니다 |

> 교훈 하나: **주입 후에 빌드가 성공했는지, 그리고 서빙되는 번들이 바뀌었는지를 확인하십시오.**
> 실패한 빌드는 조용히 "이전 것이 옳았다"를 증명합니다. 이것은 §1.5.3(포트가 응답한다 ≠ 그
> 컨테이너가 떠 있다)과 **같은 병**입니다 — 이번에는 검사가 아니라 **주입**이 대상과 독립적으로
> 참일 수 있는 신호를 읽었습니다.
>
> 교훈 둘: **주입이 실제로 무언가를 바꾸는지 먼저 따지십시오.** 위 셋째·넷째는 컴파일도 되고
> 배포도 됐지만 **행동을 바꾸지 않았습니다.** 규칙이 두 곳에 있으면 주입도 두 곳에 해야 합니다.

부수적으로 하나 더: 중단된 주입 실행들이 `UI check workbook` 탭을 **10개** 남겼고, 이후 실행이
`.filter({ hasText })`의 strict-mode 위반으로 죽었습니다. 검사기는 자기 산출물을 지우지만
**끝까지 갔을 때만** 지웁니다. 주입 루프는 매 회차 **시작 전에도** 청소해야 합니다.

그리고 방법론 하나가 값을 했습니다. 주입 harness가 외부 타임아웃으로 죽어 **`App.tsx`와
`ComposedWorkbook.tsx`에 주입된 결함을 트리에 남긴 채** 끝났는데, 사이드카 스냅샷과 "모든
수정이 파일에 실제로 있는지" 감사로 잡았습니다. **harness의 기록이 아니라 파일을 믿으십시오.**

### 1.5.8 두 엔드포인트를 서로의 증인으로 세우기 (2026-09-02)

폴리곤이 색칠 범위를 정하게 만들면서, "도형 안이 제대로 표시되는가"를 어떻게 재느냐가 문제였습니다.
지도 픽셀을 세는 것은 §1.5.5에서 이미 실패한 길이고, 서버 응답의 `inArea`가 몇 개인지만 세면
**포함 판정이 틀려도 개수는 그럴듯합니다.**

쓴 방법은 **같은 규칙을 쓰는 다른 엔드포인트를 증인으로 세우는 것**입니다.

```js
step('the drawn shape decides the colouring, by the same rule that computes its statistics',
  inside > 0 && outside > 0 && inside === statsForHalf.sampleCount)
```

트랙이 "안"이라 표시한 개수와, 통계 엔드포인트가 그 도형으로 센 표본 수가 **같아야** 합니다
(실측 587 = 587). 브라우저에 ray casting을 한 벌 더 쓰는 순간 이 등식이 깨지므로, 이 검사는
"한 규칙은 한 자리에"를 **기계가 확인할 수 있는 형태**로 바꿔 놓은 것입니다.

주입으로 확인했습니다 — 표시만 `null`로 떨어뜨리자 `0 inside / 0 outside, statistics over 587`로
실패합니다. 개수만 세는 검사였다면 이 주입은 통과했을 것입니다.

**그리고 이 검사가 데이터의 함정을 하나 잡았습니다.** 처음 폴리곤을 위경도 **범위의 중점**으로
잘랐더니 안쪽이 0개였습니다. 검사가 틀린 게 아니라, 그 세션이 바로 **GPS 튐을 증명하려고 심어
둔** 드라이브라서 최대 위도가 실제 경로보다 한참 북쪽의 이상점이었습니다 — 북쪽 절반이 빈 하늘.
**중앙값**으로 자르면 이상점과 무관하게 표본이 반씩 갈립니다(587/587).

> 교훈: 테스트 데이터를 **극단값으로 나누지 마십시오.** 이 저장소의 시드는 결함을 증명하려고
> 이상점을 일부러 심어 두었고, 그 이상점은 bbox에 그대로 들어갑니다.

### 1.5.9 주입은 "덜 하는 것"이어야지 "깨뜨리는 것"이면 안 된다 (2026-09-02)

§1.5.7에 이어 같은 자리에서 두 번 더 걸렸습니다.

| 주입 | 무슨 일이 났나 |
|---|---|
| 폴리곤 술어를 `NULL::boolean`으로 치환 | 파라미터는 그대로 바인딩되어 **`?` 개수가 어긋나 SQL이 깨졌고**, 검사는 실패가 아니라 `marked.filter is not a function`으로 **중단**됐습니다 |
| `topThree` 플래그를 `false`로 | 그 아래 검증문이 `basis=TOP3`를 **거부**해 400이 났습니다. 검사는 실패했지만 이유가 "TOP3가 고장남"이지 **"TOP3가 조용히 SERVING과 같아짐"**이 아니었습니다 |

둘째가 더 중요합니다. 진짜 위험한 결함은 **200으로 그럴듯한 답을 주는 것**이라, 주입도 그 모양이어야
증명이 됩니다. 검증을 통과시키고 질의만 바꿔치기하도록 고쳐 쓰자 원하던 증거가 나왔습니다 —
`serving 87082 -> top3 87082`. 껍질 면적이 **똑같다**는 것이 조용한 폴백의 지문입니다.

> 교훈: 주입은 대상 기능을 **하지 않게** 만들어야 하고, 응답을 **에러로 바꾸면 안 됩니다.**
> 에러는 검사가 아니라 실행을 죽이고, 그러면 그 검사가 무엇을 잡을 수 있었는지 알 수 없습니다.

### 1.5.10 아홉 개의 질의를 숫자 하나로 줄이기 (2026-09-02)

전역 필터는 "화면 아홉 개가 지키고 네 개가 무시하면 아예 없느니만 못하다"가 요구사항 자체입니다.
그래서 검사도 "필터가 동작하는가"가 아니라 **"전역인가"**를 재야 했습니다.

§1.5.8의 상호 증인을 **열두 개로 확장**했습니다. 서버가 `/api/global-filter/coverage`로
"필터를 지키는 엔드포인트 목록"을 내놓고, 시나리오는 그 목록을 읽어 각각을 두 번 — 필터 있이,
없이 — 호출한 뒤 **모든 응답의 표본 수를 집합으로 줄입니다.**

```js
const narrowSet = [...new Set(Object.values(narrowed))]
step('filtered, they all read the same narrower drive - one number, nine queries',
  narrowSet.length === 1 && narrowSet[0] < wholeSet[0] && narrowSet[0] > 0)
```

집합의 크기가 1이 아니면 실패입니다. 실측으로 필터 없이는 아홉 질의가 모두 1174, 있으면 모두
558 — JSON, CSV 행 수, GeoJSON feature 수까지 **같은 하나의 숫자**로 모입니다.

주입으로 확인했습니다. `cell-breakdown`에서 필터 절을 지우자
`{"statistics":558, ..., "cellBreakdown":1174, ...}`로 실패합니다. **엔드포인트별로 "필터를 걸면
줄어드는가"만 봤다면** 이 주입은 통과했을 것입니다 — 줄어들기는 하니까요. 하나의 숫자로 모으는
형태라야 "얼마나 줄어드는지"까지 서로 감시합니다.

> 교훈: 여러 화면이 **같은 규칙**을 따라야 하는 기능은, 화면마다 "규칙을 따르는가"를 묻지 말고
> 전부의 답을 **하나의 값으로 환원**해 보십시오. 규칙이 한 곳이면 답도 하나입니다.

한 가지 더 — 클라이언트 쪽 절반은 서버 검사로는 보이지 않습니다. 요청을 **기록**해서
"지켜야 할 경로의 요청은 전부 필터를 달았는가"와 "면제된 경로의 요청은 하나도 달지 않았는가"를
양쪽으로 물었고, 산책이 실제로 몇 개의 엔드포인트를 건드렸는지도 함께 셌습니다. 마지막 줄이
없으면 **두 개만 호출한 산책도 "전부 달았다"로 통과**합니다.

### 1.5.11 잠들어 있는 것을 겨눈 검사는 아무것도 증명하지 않는다 (2026-09-02)

"지도 레이어가 다른 측정을 지목하면 그 주행을 가져오는가"를 검사하면서 도크의 **첫 번째** 레이어
드롭다운을 바꿨습니다. 그런데 지도 페인은 **한 번에 한 레이어만 그리고**, 그 시점에 그려지고
있던 것은 두 번째 레이어였습니다. 결과는 `geometry IDENTICAL` — 기능은 멀쩡한데 검사만 실패.

§1.5.3(포트 응답 ≠ 컨테이너 기동)과 같은 계열이지만 방향이 반대입니다. 그때는 **대상과 무관하게
참일 수 있는 신호**를 읽었고, 이번에는 **대상이 읽지 않는 입력**을 건드렸습니다. 둘 다 "검사가
보는 것"과 "기능이 보는 것"이 다른 경우입니다.

고친 방법은 검사를 **그려지고 있는 레이어에 맞추는 것**이었고(먼저 체크박스를 켜고 그 레이어의
드롭다운을 바꿈), 그러자 `fetched 3 (other is 3), geometry changed`가 나왔습니다.

> 교훈: 검사를 쓰기 전에 **"기능이 지금 이 입력을 읽고 있는가"**를 먼저 확인하십시오.
> 배타적 선택(한 번에 하나만 활성)이 있는 UI에서 특히 잘 걸립니다.

### 1.5.12 증인을 세울 수 없는 결함도 있습니다 — 그러면 그렇다고 적으십시오 (2026-09-02)

상태 기계가 내는 구간이 **주행을 넘어가지 않는지**를 시나리오로 재려고 했습니다. 주입은
명백합니다 — 윈도우에서 `PARTITION BY session_id`를 빼면 한 주행의 마지막 열린 구간이
다음 주행의 첫 표본에서 닫힙니다.

**그런데 숫자가 하나도 안 움직였습니다.** 6개 그대로, 값도 그대로.

이유가 이 항목의 요점입니다. `seq`는 **주행마다 0부터 다시 시작합니다.** 파티션을 빼면
`min(seq) FILTER (...)`가 고른 진입 seq가 그 에피소드 안의 **여러 주행에서 동시에** 매칭되고,
뒤이은 `max(ts) FILTER (WHERE seq = 진입seq)`가 엉뚱한 주행의 시각을 집어 옵니다. 결과는
"틀린 값"이 아니라 **아무 행도 안 나오는 것**입니다. 조건 `exit > entry`가 깨지기 때문입니다.

시드를 비틀어 봐도 마찬가지였습니다. 초기 상태 조건을 프론트홀 세션에서만 참이 되게 만들어
"세션 1에서 진입하고 세션 4에서 빠져나오는" 구간을 강제해도 같은 이유로 0행입니다.

> **파티션 키가 동시에 정렬 키이고 그 값이 파티션마다 반복되면, 파티션을 잃은 질의는
> 틀린 답이 아니라 빈 답을 냅니다.** 그리고 빈 답은 "이 드라이브에 그런 구간이 없다"와
> 구별되지 않습니다.

그래서 두 가지를 했습니다.

1. **진짜 가드는 컴파일된 SQL을 읽는 단위 테스트로** 옮겼습니다
   (`KpiGraphTest.everyWindowInTheLadderIsPartitionedByDrive`). 주입하면 실패합니다 —
   실측 확인했습니다.
2. 시나리오에 남은 단언은 **"bound, not a witness"라고 이름에 적었습니다.** 지우지 않은
   이유는 다른 결함(너무 긴 구간을 내는 종류)은 여전히 잡기 때문이고, 이름에 적은 이유는
   **통과하는 검사를 증거로 오해하는 것이 결함보다 오래가기** 때문입니다.

> 교훈: 주입해도 안 움직이는 검사를 만나면 셋 중 하나입니다 — 주입이 틀렸거나(§1.5.7·§1.5.9),
> 검사가 엉뚱한 것을 보고 있거나(§1.5.1), **이 데이터로는 그 결함이 관측 불가능하거나.**
> 셋째라면 검사를 지어내지 말고 **어디에 진짜 가드가 있는지 적고 이름을 낮추십시오.**

### 1.5.13 빈 집합 위의 단언은 언제나 통과합니다 (2026-09-03)

코호트 화면의 교란 가드를 검사하며 두 단계를 나란히 썼습니다.

```js
step('holding a dimension constant is the default when the axis is the build',
  held.holdConstant === 'SCENARIO' && held.excluded.length > 0, …)
step('each excluded measurement is named, and really does have the odd value',
  wronglyNamed.length === 0 && held.excluded.every((e) => e.why.includes(…)), …)
```

가드를 무력화하는 주입(`holdConstant()`가 전부 그대로 돌려주기)을 걸었더니 **첫 단계는
실패하고 둘째는 통과**했습니다. `every`는 빈 배열에서 참이기 때문입니다. 둘째 단계는
"제외된 것이 전부 제대로 이름 붙었다"를 말하는데, **제외된 것이 하나도 없으면 그 문장은
공허하게 참**입니다.

이것이 §1.5.1(대상과 무관하게 참일 수 있는 신호)의 특수한 모양이고, 특히 흔한 이유는
`every`·`all`·`none`·`filter(...).length === 0` 계열이 전부 이 성질을 갖기 때문입니다.

> **`every` 계열의 단언은 반드시 "집합이 비어 있지 않다"와 짝을 지으십시오.** 짝은 같은
> 단계 안에 넣거나(`xs.length > 0 && xs.every(…)`), **바로 앞 단계가 개수를 단언하게**
> 하십시오. 여기서는 후자를 택했습니다 — 두 문장이 서로 다른 것을 말하고, 실패했을 때
> 어느 쪽이 깨졌는지가 이름에서 바로 읽히기 때문입니다.

같은 검사 묶음에서 하나 더 나왔습니다. "그룹의 최소·최대는 멤버들의 최소·최대"라는 단언은
**시드 데이터에서 우연히 약합니다** — 주행 하나만 읽는 결함(I9)을 걸어도 그 주행의 최소·최대가
마침 풀링된 값과 같아 통과했습니다. 같은 단계의 **중앙값** 쪽이 잡았습니다. 두 방식으로 재는
단계를 쓸 때, 둘 중 하나만 판별력이 있을 수 있다는 것을 알고 쓰는 것과 모르고 쓰는 것은
다릅니다.

### 1.5.14 감사 목록에서 빠진 항목은 검사할 대상 자체가 없습니다 (2026-09-03)

전역 필터의 도달 범위는 `GlobalFilter.coverage()`가 목록으로 갖고 있고, S20이 그 목록을 읽어
**지키는 경로는 조건을 실었는지 · 면제 경로는 안 실었는지**를 봅니다. 잘 도는 장치입니다.

그런데 `/distance-bins`는 **어느 쪽에도 없었습니다.** `filter` 파라미터 자체를 받지 않았고,
지킴 목록에도 면제 목록에도 이름이 없었습니다. 그 상태에서 S20은 **무엇을 해도 통과합니다** —
읽는 신호가 "목록에 있는 경로들의 행동"인데, 이 경로는 목록에 없으니까요.

화면에서는 이렇게 보였습니다. `cell:210`을 걸면 경로 색·범례·통계·CDF·셀 막대·지도 타일이
전부 좁아지고, **그 옆의 거리 프로파일만 전 주행을 그렸습니다.** 면제라는 표시도 없었습니다.

> **틀린 항목은 검사가 잡지만, 없는 항목은 검사할 대상이 없습니다.** 목록으로 감사하는 장치를
> 만들 때는 **목록의 완전성 자체를 다른 방법으로** 재야 합니다. 여기서 쓴 방법은 한-숫자
> 축약(§1.5.10)입니다 — 거리 프로파일의 표본 합계를 나머지 아홉 질의와 **같은 숫자**여야 하는
> 것으로 묶었으므로, 목록에서 빠지면 축약이 깨집니다.

### 1.5.15 UI 배선을 검사하려면 UI를 몰아야 합니다 (2026-09-03)

서버가 계산해 놓고 화면이 닿지 않던 아홉 가지를 배선하면서, 그 아홉에 대한 검사를 썼습니다.
둘이 이런 모양이었습니다.

```js
step('the screen offers it rather than leaving it to the API',
  sepOptions.includes(';'), …)               // 구분자 <option>이 있는가
step('both comparison screens offer it, not just Statistics',
  meanIn === 1 && meanInCompare === 1, …)    // <select>가 하나씩 있는가
```

**둘 다 배선을 지워도 통과했습니다.** 폼이 `delimiter`를 안 보내도 `<option>`은 그대로 있고,
요청이 `domain`을 안 실어도 `<select>`는 그대로 있습니다. **존재하지만 아무것도 보내지 않는
컨트롤은 동작하는 컨트롤과 화면상 완전히 같습니다** — §1.5.1의 특수한 경우이고, 하필 §1.5.1을
쓴 사람이 같은 자리에서 다시 빠졌습니다.

고친 형태는 둘 다 **행동**을 봅니다. 구분자는 실제 파일 입력에 세미콜론 파일을 넣고 `,`로는
거부되고 `;`로는 3표본이 들어오는 것을 보고, dB/선형은 셀렉트를 바꾼 뒤 **표의 숫자가
−80.93에서 −65.53으로 움직이는 것**을 봅니다.

> **컨트롤을 세지 말고 컨트롤이 바꾸는 숫자를 보십시오.** API를 직접 호출해 서버가 옳음을
> 보이는 것은 서버 검사이지 배선 검사가 아닙니다 — 그리고 배선이야말로 이 부류의 작업에서
> 유일하게 새로 생긴 것입니다.

### 1.5.16 한 술어에 무조건 참인 가지가 있으면 그 검사는 검사가 아닙니다 (2026-09-03)

푸트프린트 셀 필터를 검사하려고 이렇게 썼습니다.

```js
step('the cell filter narrows what is drawn, and the map says what it left out',
  after < before && new RegExp(`${allCells.length - 2} .*fewer|2 of ${allCells.length}`)
    .test(note) === false
    ? after < before && /of \d+ cells/.test(note)
    : true,                                   // ← 이 가지
  …)
```

**세 겹의 결함이 한 줄에 있습니다.**

1. 중첩 삼항의 `: true` 가지는 **아무것도 재지 않습니다.** 정규식이 맞기만 하면 그린 개수는
   보지 않고 통과합니다.
2. `after < before`는 **좁아졌다**만 말합니다. 다섯 중 둘을 남기라고 했는데 **엉뚱한 셋**을
   지워도 참입니다.
3. 그리고 실제로 이 검사는 **푸트프린트를 아예 그리지 않는 탭**(Overview)에서 돌고 있었고,
   `path.leaflet-interactive`를 셌습니다 — 그 선택자에 걸린 229개는 전부 **경로 선분**이었습니다.
   즉 켜지지도 않은 기능에 대해 상수 두 개를 비교하고 있었습니다.

고친 형태는 정확히 셉니다. 껍질에 `className: 'footprint-hull'`을 주어 **경로와 따로 세지고**,
술어는 `before - after === allCells.length - 2` — 다섯 중 둘을 남기면 **정확히 셋**이 사라져야
합니다. 그리고 머리글이 `2 of 5 cells`라고 적는지 함께 봅니다.

> **`<` 는 좁아졌다는 뜻이지 옳게 좁아졌다는 뜻이 아닙니다.** 그리고 화면 요소를 셀 때는
> **기능이 그린 것만 세지는 선택자**가 필요합니다 — 없으면 만들어야 합니다. 셀 수 있게
> 만드는 한 줄이, 세는 척하는 검사보다 쌉니다.

### 1.5.17 화면이 **주지 않는** 컨트롤은, 컨트롤을 세는 검사에게 동작하는 것과 같습니다 (2026-09-03)

툴바의 그룹 다섯이 열네 탭 전부에 그려지고 있었고, 그것을 **소비하는 화면은 셋**이었습니다.

| 컨트롤 | 안 되는 탭에서 무슨 일이 일어나나 |
|---|---|
| `Ask an area` | 버튼이 파랗게 되고 `Drawing…`으로 바뀝니다. 지도 커서는 손 모양 그대로고, 클릭하면 지도가 밀립니다. 되돌리는 길은 버튼을 한 번 더 누르는 것뿐입니다 |
| `Area bins` | 요청이 나가고 지도는 그대로입니다. 그리고 **통계 셀렉트가 하나 더 생겨** 그것도 아무 일을 안 합니다 |
| `Distance bins` | 주소에 `ds=250`이 붙고 아무것도 그려지지 않습니다. 그 상태로 공유한 링크는 죽은 설정을 갖고 열립니다 |
| `Colour by: Serving cell (PCI)` | 열네 탭 **전부에서** 범례가 PCI census로 바뀌고, 그 색으로 칠하는 지도는 셋뿐입니다 |
| Layers 도크 스위치 | Overview에서만 그려지는데 **공유 상태에 씁니다.** 여기서 이벤트를 끄고 Mobility로 가면 다시 켜져 있습니다 |

**검사기 셋 다 초록이었습니다.** 각 컨트롤에 대한 검사가 하나씩 있었고, 전부 **그 컨트롤이
동작하는 탭에서** 몰고 있었기 때문입니다. §1.5.15가 "컨트롤을 세지 말고 컨트롤이 바꾸는
숫자를 보라"고 적었는데, 여기서는 숫자까지 봤습니다 — **한 탭에서만** 봤습니다.

그리고 이것은 §1.5.1의 특수한 경우가 아니라 그 반대입니다. 신호는 진짜였고(숫자가 정말
움직였고) 검사가 고른 **표본**이 편향돼 있었습니다. 열네 탭 중 하나를 고르면서, 그 하나를
"컨트롤이 동작하는 곳"으로 고른 것입니다.

고친 방식은 코드 쪽이 먼저입니다. `App.tsx`의 `WORKBOOKS` 표에 `reads` 열이 생겨 화면마다
어느 그룹을 소비하는지 **한 자리에서** 답합니다 — 같은 결함이 범례에서 났을 때 만든
`isolates` 열 옆입니다. 컨트롤은 그 답이 참인 탭에서만 그려집니다.

> **효과가 화면에 따라 달라지는 컨트롤은, 검사가 화면을 이름으로 지목해야 합니다.**
> 그리고 코드는 "이 화면이 이것을 읽는가"에 **한 곳에서** 답해야 합니다 — 답이 열네 군데에
> 흩어져 있으면 그중 열한 군데가 틀려도 아무 검사가 실패하지 않고, 실제로 그랬습니다.
> 이 부류를 겨누는 검사의 값싼 형태는 **부정 검사**입니다: 컨트롤을 소비하지 않는 탭에서
> 그것이 **그려지지 않는지** 보는 것. 열네 번 몰아 보는 것보다 싸고, 표를 고치는 것을
> 잊으면 바로 빨개집니다.

### 1.6 API 표면 커버리지 — "뷰 없는 로직"을 정면으로 겨냥

타입 체크가 못 보는(타입은 정상) 그리고 E2E가 못 보는(없는 화면의 테스트를 아무도 안 씀) 영역입니다.
**서버가 할 수 있는 것**과 **클라이언트가 실제로 호출·렌더하는 것**을 대조하면 보입니다.

`tools/uxtest/api-surface.mjs`가 세 가지를 봅니다.

1. 서버가 노출한 REST 엔드포인트 중 API 클라이언트가 호출하지 않는 것
2. API 클라이언트 메서드 중 어떤 컴포넌트도 부르지 않는 것
3. 서버가 정의한 KPI 중 실행 중인 UI에서 도달할 수 없는 것

**이 저장소에 돌린 결과 — 제 코드에서 실제 결함 3건이 나왔습니다.**

```
GET /api/import/jobs   임포트 이력 API를 만들고 아무 데도 안 그림
api.statistics()       통계 + 101점 CDF를 만들고 화면에 없음
api.session()          선언만 하고 아무도 호출 안 함
```

두 번째가 특히 뼈아픕니다. 저는 그 CDF 쿼리를 **2.8초에서 0.086초로 최적화하고 신중하게 측정까지
했는데**, UI에서 그걸 부르는 코드가 없었습니다. **아무도 도달할 수 없는 빠른 코드도 결함입니다.**
그리고 그걸 보려면 다른 종류의 검사가 필요했습니다.

세 건 모두 조치했습니다 — Statistics 워크북 페이지(요약 통계 + p05/p50/p95 표시된 CDF), 임포트 이력
화면, 그리고 안 쓰는 클라이언트 메서드는 **화면을 만들어주는 대신 삭제**. 지금은 `no gaps`입니다.

비용은 수 초, 출력은 몇 줄입니다. 매 변경마다 돌릴 수 있는 수준입니다.

## 2. Q2 — 자동 검출과 수정

### 2.1 검출: 브라우저가 공짜로 주는 신호부터

Playwright가 노출하는 것들이고, 런타임 비용이 사실상 0입니다.

| 이벤트 | 잡는 것 |
|---|---|
| `page.on('pageerror')` | 처리되지 않은 예외 |
| `page.on('console')` (type `error`) | `console.error`. `location()`이 파일/줄/열을 줌 → **수정 좌표** |
| `page.on('requestfailed')` | 실패한 네트워크 요청 |
| `page.on('crash')` | 페이지 크래시 |

**`pageerror`가 놓치는 것**: 처리되지 않은 Promise 거부. React 에러 경계도 이건 못 잡습니다.
`addInitScript`로 `unhandledrejection` 리스너를 심어야 합니다. (Playwright 이슈 #14165에 Firefox가
promise 거부에 대해 `pageerror`를 발화하지 않는 것이 기록되어 있습니다.)

이 저장소의 검증 스크립트는 이미 앞의 세 개를 수집하고, 앱 코드 오류와 환경적 실패(차단된 지도 타일)를
분리해서 판정합니다. 그 분리가 없으면 스위트가 상시 빨간불이 되어 아무도 안 봅니다.

### 2.2 피드백 형식이 "수정 가능성"을 결정한다

검출과 수정은 다른 문제입니다. **실패했다는 사실보다 실패 메시지의 모양이 더 중요합니다.**

실험에서 관찰한 두 가지 나쁜 형식:

- **크래시는 나쁜 실패입니다.** D3에서 제 단언 스위트는 `.panel`을 기다리다 30초 타임아웃으로
  프로세스가 죽었습니다. 종료 코드는 비정상이니 "뭔가 잘못됐다"는 알려주지만, 스택 트레이스는
  Playwright 내부를 가리키지 앱을 가리키지 않습니다. **깨끗한 `FAIL` 한 줄이 크래시보다 낫습니다.**
- **선택자 종류가 진단 가능성을 좌우합니다.** `getByRole('button', {name:'Submit'})` 실패는
  "이런 이름의 버튼이 있어야 하는데 없다"를 말합니다. `getByTestId('btn-1')` 실패는 아무것도
  말해주지 않습니다. Playwright와 Testing Library의 공식 우선순위가 일치합니다 — role, 그다음
  label/placeholder/text, **testId는 마지막**.

### 2.3 픽셀 diff는 진단이 아니라 트립와이어로

`toHaveScreenshot({ maxDiffPixelRatio })`는 a11y 트리가 못 보는 순수 스타일 회귀(색, 레이아웃 붕괴,
겹침)를 잡습니다. 다만 **실패 출력이 에이전트에게 거의 쓸모가 없습니다** — "N pixels (ratio R) are
different" 뿐이고, 비율은 소수점 2자리로 반올림되어 1% 미만은 전부 `0.01`로 뭉개지며 위치 정보가 없습니다.

실용적 조합: 픽셀 비율은 **심각도 스칼라**로만 쓰고, 실제 진단은 DOM에서 가져옵니다 —
의심 구간에 대해 `getBoundingClientRect`/`getComputedStyle`을 `page.evaluate`로 읽는 편이
PNG를 모델에 넣는 것보다 싸고 정확합니다.

그리고 픽셀 기준선은 **브라우저·OS·폰트가 고정되지 않으면 상시 거짓 양성**입니다. 고정된 컨테이너
이미지 안에서만 돌리는 것이 사실상 필수 조건입니다.

### 2.4 결정론이 자동 루프의 전제 조건

자율 루프에서 지배적 비용은 진짜 실패가 아니라 **flake**입니다. flake 한 번이 탐지–진단–수정 사이클을
통째로 태우고, 심하면 **에이전트가 멀쩡한 코드를 "고치게"** 만듭니다.

네 축을 각각 고정해야 합니다.

| 축 | 방법 |
|---|---|
| 시간 | `page.clock.install()` — **다른 clock 호출보다 먼저**(문서화된 제약). `Date`, 타이머, `requestAnimationFrame`, `performance`까지 고정하므로 rAF 기반 JS 애니메이션도 잡힙니다 |
| 애니메이션 | `toHaveScreenshot`은 기본이 `animations: 'disabled'` |
| 무작위성 | `addInitScript`로 `Math.random` / `crypto.randomUUID` 고정 |
| 데이터 | `page.route`로 고정 픽스처 |

이 저장소는 시드 데이터가 **결정론적 생성기**(고정 시드)로 만들어지고 시간축이 고정된 세션이라,
§1.3의 노이즈 바닥이 0으로 나왔습니다. 그게 diff 기반 검출을 쓸 수 있게 해준 전제입니다.

> 과다 마스킹 주의: `mask` 처리한 영역은 **영원히 회귀를 놓칩니다.** 마스크는 테스트 억제와 같으므로
> 리뷰 대상이어야 합니다.

### 2.5 "자동 수정"은 어디까지 실재하는가

정직하게: **실패한 UI 테스트가 애플리케이션 코드를 자동으로 고치는, 검증된 상용 시스템은 찾지
못했습니다.** 실재하는 것은 **테스트 쪽 자가 치유**입니다.

`npx playwright init-agents --loop=claude`가 planner/generator/**healer**를 설치합니다. healer는
실패한 단계를 재생하고 살아있는 UI에서 동등한 요소를 찾아 **테스트 코드**를 고칩니다.

여기에 반드시 경계선이 필요합니다.

> **healer는 테스트만 고칩니다. 컴포넌트는 절대 고치지 않습니다.**
> 그리고 위험이 있습니다 — 과열된 healer는 **기대값을 고쳐써서 진짜 회귀를 덮어버릴 수 있습니다.**
> 실무 규칙: healer의 패치는 **선택자·대기 변경만 수용하고, 기대값 변경은 거부**합니다.
> healer가 "고치는 대신 테스트를 skip하겠다"고 판단하는 순간이 **애플리케이션 쪽이 깨졌다는 신호**이며,
> 거기서 앱 수정 담당으로 넘겨야 합니다.

### 2.6 실무적 자동 루프 설계

```
변경
 └─ 1. typecheck + build            (초 단위, 컴파일 오류)
 └─ 2. API 표면 커버리지            (초 단위, 뷰 없는 로직)      ← §1.6
 └─ 3. 런타임 오류 싱크 + 라우트 다이제스트  (~10초, ~1 KB 피드백)
 └─ 4. 행위 단언 스위트             (분 단위, 상호작용)
 └─ 5. 픽셀 트립와이어              (선택, 고정 이미지 안에서만)
        │
        └─ 실패 → 구조화된 실패 1건만 컨텍스트로 (스크린샷 아님)
                  → 수정 → 2번부터 재실행
```

핵심은 **실패했을 때 모델에 넣는 것이 스크린샷이 아니라 몇십 바이트의 구조화된 실패**라는 점입니다.
§1.1 기준으로 스크린샷 1장 = 실패 단언 120건 분량입니다.

## 3. Q3 — UX-driven development

### 3.1 먼저 정직한 답: 용어 자체가 표준이 아닙니다

조사 결과 **"UX-driven development"에는 정본 정의도, 표준화 기구도, 기원 논문도 없습니다.**
TDD·BDD·ATDD가 각각 명시적 창시자를 갖는 것과 달리, 이건 벤더/에이전시의 마케팅 용어입니다.

따라서 "UXDD의 best practice"를 그대로 찾는 것은 불가능하고, **실제로 근거가 있는 인접 실천들**로
분해해서 보는 편이 정확합니다.

### 3.2 근거의 질을 구분해서

| 실천 | 근거 수준 |
|---|---|
| **BDD 명세는 시간이 지나면 썩는다** | **동료심사 실증.** Binamungu et al. (SANER 2018), 26개국 75명 설문: **61%가 "중복 때문에 기능이 사실상 동결된다"**, 49% 실행 시간 증가, 43% 이해도 저하 |
| **Gherkin을 UI 어휘로 쓰면 망가진다** | Cucumber 자사 블로그가 **anti-pattern #1**로 명시. "버튼", "링크" 같은 UI 어휘가 들어가면 레이아웃이 바뀔 때마다 깨지고 도메인 학습도 안 됨 |
| **test-first가 결함을 줄인다** | **엇갈림.** Nagappan et al. 2008(MS/IBM 4개 팀): 출시 전 결함 밀도 40–90%↓, 초기 개발 시간 15–35%↑. 그러나 **가장 큰 메타분석**(Rafique & Misic 2013, 27개 실험)은 **품질에 작은 양의 효과, 생산성에는 유의미한 효과 없음** |
| **스토리 맵 기반 저니 단위 작업** | **측정된 근거 없음.** 널리 쓰이는 실무 기법이지만 결함·재작업 감소를 측정한 통제 연구를 찾지 못함 |
| **접근성이 테스트 가능성을 만든다** | 논리적으로 견고, 수치는 벤더 자료. axe "약 57%"는 **Deque 자사 연구이며 분모가 이슈 '건수'** |

> **메타분석이 헤드라인보다 중요합니다.** "TDD가 결함을 90% 줄인다"만 인용하는 것은 부정직합니다.
> 27개 실험을 모은 결과는 훨씬 온건합니다.

### 3.3 그래도 실질적으로 유효한 것 — 그리고 이 저장소에서 검증된 것

**(1) 역할·접근가능한 이름을 선택자의 기준으로 삼기**

접근성을 위해 시작하지만 **부수효과로 UI가 기계 검증 가능해집니다.** 접근가능한 이름이 없으면
테스트를 쓸 수조차 없으므로, 작성 시점에 강제됩니다.

WebAIM Million 2026: 100만 홈페이지 중 **95.9%**가 자동 검출 가능한 WCAG 실패를 가짐. 상위 6개 중
4개(대체 텍스트, 폼 레이블, 빈 링크, 빈 버튼)가 **정확히 "접근가능한 이름 없음"** 계열입니다.

**(2) UI 어휘를 명세에서 몰아내기**

Gherkin을 쓴다면 도메인 포트에 바인딩하고, 페이지 객체에 바인딩하지 않습니다. 시나리오에 위젯 명사가
들어가면 안 됩니다. 대신 UI 검증은 별도 계층(컴포넌트 상호작용 테스트 + 얇은 저니 스위트)으로 둡니다.

**(3) 저니는 E2E로, 상태 조합은 컴포넌트로**

Component-Driven Development는 명시적으로 상향식이라, **조립된 저니가 말이 되는지는 아무것도
검증하지 않습니다.** 반대로 E2E로 모든 상태 조합을 도는 건 비현실적입니다.
경험칙: **E2E는 이음매를 증명하고, 컴포넌트 테스트는 상태를 증명합니다.**

**(4) 이 저장소에서 실제로 해본 것**

Nemo 리서치에서 "기존 사용자가 몸으로 익힌 상호작용" 3가지를 먼저 특정하고, **구현 전에 그것을
검증 항목으로 박아 넣었습니다** — 공유 시간 커서, 워크북 탭, 임계 강조.

결과적으로 그 셋은 이후 모든 리팩터링(SQL 재작성, 파티셔닝, 데시메이션, 폴리라인 그룹화)에서
살아남았습니다. 스키마와 쿼리를 전부 갈아엎는 동안에도 **"커서를 움직이면 값이 따라온다"는 단언이
계속 지켜졌습니다.** 이게 UX를 먼저 고정하는 것의 실질적 효용입니다 — 내부는 마음껏 바꾸되 사용자가
체감하는 계약은 고정됩니다.

다만 §1.5에서 드러났듯 **그 단언 중 하나는 실제로는 아무것도 검사하지 않고 있었습니다.**
UX를 먼저 정하는 것과, 그 UX가 지켜지는지 실제로 검증되는 것은 별개입니다.

### 3.4 디자인 토큰에 대한 주의

W3C Design Tokens 포맷은 **Community Group 초안**이며, 현재 초안 본문이 구현자에게
**"이 버전을 구현하지 말라"**고 적고 있습니다. 토큰 파이프라인 자체는 유효한 실천이지만
(단일 소스에서 생성, 산출물은 절대 손으로 수정 안 함), **표준으로 확정된 것처럼 인용하면 안 됩니다.**

사실 검증 단계에서 무너진 것들입니다.

| 주장 | 왜 틀렸나 |
|---|---|
| Playwright MCP의 "스냅샷 200–400 / 스크린샷 3,000–5,000 토큰" | **벤더 자체 근사치**이며 측정 벤치마크가 아님. 데이터 밀도 높은 화면에서는 제 실측과 어긋남 |

| "TDD가 결함 40–90% 감소"만 인용 | 가장 큰 메타분석은 **작은 양의 품질 효과, 생산성 효과 없음** |
| W3C Design Tokens가 확정 표준 | **Community Group 초안**, 본문이 구현하지 말라고 명시 |

| `innerText`가 `textContent`보다 런타임 비용이 크다(레이아웃 유발) | 근거 확인 실패 |
