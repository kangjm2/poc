⑨ 입력 기준 분류와 사용자 시나리오

유즈케이스 31개를 입력 데이터로 다시 묶고, 그 묶음으로 업무의 처음부터 끝까지를 시나리오 7편으로 푼 것
← 브리프 목록 · ⑦ 상세 · ⑧ 요약표 · 대조표 · E2E 검증 여정

매뉴얼의 유즈케이스는 기능 하나를 다룹니다 — 지도에 셀 선을 긋는다, 파라미터 두 개를 겹친다, 색상셋을 만든다. 그러나 사용자가 실제로 하는 일은 "드롭콜 23건이 왜 떨어졌는지 알아내서 조치 목록을 내는 것"처럼 여러 기능을 순서대로 거쳐 하나의 결정에 이르는 흐름입니다. 이 문서는 그 흐름을 쓰기 위한 준비로 유즈케이스를 장·절이 아니라 필요한 입력으로 다시 묶고(§2), 그 묶음을 합쳐 시나리오 7편을 씁니다(§3). 먼저 이 작업이 설계 과정의 어느 단계에 속하는지부터 적습니다(§1).

1. 설계 관점에서 이 작업이 놓이는 자리

요구사항 공학에서 유즈케이스는 시스템 경계 안의 기능 단위이고, 시나리오는 그 유즈케이스 여럿을 실제 업무 순서로 꿴 구체적 사례입니다. 시나리오를 쓰는 일은 요구 분석 단계의 끝, 설계에 들어가기 직전에 놓입니다. 기능 목록이 다 모였을 때 "이 기능들로 사용자의 업무가 끊기지 않고 끝까지 이어지는가"를 검사하는 것이 시나리오의 첫 용도이고, 같은 시나리오가 검증 단계에서 인수 기준으로 다시 쓰이는 것이 둘째 용도입니다. V 모델로 말하면 왼쪽(분석)에서 쓴 시나리오가 오른쪽(검증)의 E2E 테스트가 됩니다.

이 문서의 시나리오는 검증 여정 S1–S13이 레퍼런스가 상정한 업무를 빠짐없이 덮는지 대조하는 기준이기도 합니다 — §4의 대응표가 그 대조입니다.

입력 기준 분류가 이 단계에서 하는 일은 둘입니다. 첫째, 우선순위를 "유즈케이스 몇 개를 덮나"가 아니라 "입력 하나를 채우면 시나리오 몇 편이 끝까지 열리나"로 매기게 합니다. 둘째, 그 입력이 우리 데이터 모델에 없다면 그것은 화면이 아니라 스키마의 결정 사항이라는 것을 드러냅니다(active set 구분, BTS 파일의 열). 시나리오가 화면 설계에 앞서야 하는 이유가 여기에 있습니다 — 화면은 바꾸기 쉽고 스키마는 어렵습니다.

2. 입력 데이터 기준 분류

기준은 "그 입력이 없으면 유즈케이스가 성립하지 않는 것"입니다. 좌표 있는 측정 파일은 거의 모든 유즈케이스의 바탕이라 그룹 ⑥ 하나로만 둡니다. 각 유즈케이스가 요구하는 입력의 원문은 ⑦ "필요한 입력 데이터 — 31개 한 표"에 있습니다.

장·절 묶음과 다른 점

장 기준으로는 UC2와 UC11이 8장 안에서 멀리 떨어져 있고, UC27(KPI Workbench)과 UC20(Pilot pollution)이 다른 장에 있지만, 입력 기준으로는 둘 다 "active set을 구분하는 이웃 측정"이라는 같은 전제를 공유합니다. 반대로 12장 색상셋 네 개(28–31)는 입력 기준으로 ⑥ · ⑥ · ⑨ · ③으로 흩어집니다. 우리 데이터와 맞춰 보면 ⑥ · ④는 있고, ⑤ · ⑦ · ③은 일부, ① · ② · ⑧은 없고, ⑨는 범위 밖입니다. 그룹 하나를 채우면 여러 유즈케이스가 한꺼번에 열리는 곳은 ⑦(BTS 열 보강)과 ⑤(active set 구분)입니다.

3. 사용자 시나리오 7편

시나리오마다 사용자의 질문, 합쳐지는 입력 그룹, 유즈케이스를 순서대로 꿴 흐름, 마지막에 내리는 결정을 적습니다. 흐름의 유즈케이스는 번호 옆에 매뉴얼의 제목(Subject)을 붙였고, 절차와 대화상자 값은 ⑦에 그대로 있습니다. 유즈케이스 밖의 단계(적재 규칙 · 드릴다운 · 리포트 · 스케줄러)는 레퍼런스 폴더의 전사 5편을 가리킵니다. 각 시나리오 끝의 상자는 우리 구현의 현재 상태와 가장 가까운 검증 여정입니다.

  2. UC3Viewing IP/UDP packet trace data 무선이 멀쩡하면 그 시각의 패킷을 열어 재전송 · RTT · 윈도우를 본다.
  3. UC4Viewing Binary Log Data 스케줄링 의심이면 진단 로그의 MAC/RLC 상태를 본다.

결정. 무선 파라미터 조정 vs 서버 · 전송 쪽 이관.

우리
1단계(무선 층)만 됩니다. 패킷 캡처와 바이너리 로그는 입력에 없고 시그널링 본문은 비구조화입니다. 같은 질문을 프론트홀 쪽으로 던진 것이 검증 여정 S4 프론트홀 결함 분류 — 레퍼런스에는 없는 우리 쪽 시나리오입니다.

시사점

  • A와 B는 같은 결손을 공유합니다 — active set 구분(⑤)과 BTS 열 보강(⑦). 이 둘을 채우면 시나리오 두 편이 한꺼번에 끝까지 이어집니다. 유즈케이스 단위로 세면 20 · 21 · 27과 17 · 19 · 23 여섯 개이지만, 시나리오 단위로 보면 "드롭콜 원인"과 "사이트 DB 검증"이라는 업무 두 개가 완성되는 것입니다.
  • C는 화면이 아니라 출력이 부족합니다. 분석은 되는데 리포트로 나가지 않습니다. 백로그의 "리포트 구성 선택"이 이 시나리오의 마지막 단계입니다.
  • D · E · F는 입력을 바꾸지 않는 한 부분적으로도 열리지 않습니다. 수집 범위(CSV 한 개 = 세션 한 개)의 결정이며, 유즈케이스 대조표에서 ✕로 표시된 것과 같은 항목입니다. 다만 E의 질문 자체는 우리가 프론트홀 방향으로 이미 답하고 있습니다(S4).
  • G는 인프라 결정입니다. 폴더 감시 · 스케줄 · 메일은 분석 기능이 아니라 운영 기능이라, 도입 여부를 따로 정해야 합니다.
  • 검증 여정에 없는 시나리오는 D · F 둘입니다. 나머지 다섯은 우리 여정이 부분적으로라도 걷고 있으므로, 새 여정을 만들기보다 기존 여정의 끊긴 단계를 늘리는 쪽이 맞습니다.
