지금까지 우리 격차 분석은 스크린샷 판독과 마케팅용 Technical Overview에 근거했습니다. 메뉴 설명도, 사용자 절차도 없는 자료였습니다. 505페이지 사용자 가이드를 읽고 나서 그 판단들이 확인된 것과 틀린 것으로 갈렸습니다. 이 문서가 그 결산입니다.

1. 확인된 것

우리 판단매뉴얼
노드 그래프의 구조 — 소스 → 결합 → 연산 → 상태 → 출력 맞음 UC27이 그 화면을 만드는 절차를 그대로 기술합니다. 노드 배치, 연결 방향, 상태 이름(OK/Bad BLER/Missing handover)까지 일치 p403–410
정렬 노드를 넣지 않음 — "우리 행 집합은 seq 키라 정렬할 것이 없다" 근거까지 맞음 레퍼런스가 정렬이 필요한 이유는 Union이 순서를 파괴하기 때문입니다 ("in no particular order") p359. 우리는 Union이 없습니다
Weight by time을 만들지 않음 맞음 시간 가중이 필요한 이유는 Nemo 파일이 시간 기반이라 표본 길이가 제각각이기 때문입니다. 우리는 1 Hz 균일이라 가중 없는 평균이 맞습니다 p353·375·378. 단 거리 축은 여기 속하지 않습니다 — 아래 C7 정정
Resample을 만들지 않음 맞음 같은 이유. 재표본화할 불규칙성이 없습니다
파일럿 오염에 하한 조건 (best RSRP ≥ −110) 같은 설계, 다른 값 2026-09-02 정정: 첫 판은 "매뉴얼의 UC20에는 이 조건이 없다"고 적었으나, 원문 p173의 필터에 RSCP active set best above threshold = -95가 있습니다. 하한의 존재는 같고 값만 다릅니다(−95 대 −110). 없으면 커버리지 홀이 파일럿 오염으로 오탐됩니다 — 모든 셀이 똑같이 약하면 "여러 셀이 비슷하게 강함"이 참이 되니까요
필터를 텍스트 조건식으로 우리가 더 나음 레퍼런스는 이진 트리라 한 노드에 자식이 둘뿐이고, 조건을 다이얼로그로 하나씩 조립해야 합니다 UC26, p396

2. 뒤집힌 것

C1. Missing neighbour는 막혀 있지 않았습니다

기존"측정된 이웃과 설정된 이웃 목록의 차집합인데 우리는 후자가 없습니다" — 격차표의 (a) 데이터 모델이 막음
매뉴얼Nemo는 설정된 이웃 목록을 쓰지 않습니다. 측정값만으로 판정합니다 — "if Ec/N0 1. best is better than Ec/N0 best active set, the handover has not occurred" UC27, p404
실제 원인우리 시드 생성기. 매 표본 argmax를 서빙 셀로 고르기 때문에 "이웃이 서빙보다 강한" 표본이 정확히 0개입니다 — 커밋 9262db0의 정합성 불변식 #2가 그것을 단언하고 통과합니다
조치격차표에서 (a) → (b) 실제로 남은 작업으로 이동. 생성기에 핸드오버 지연(time-to-trigger, 히스테리시스)을 넣으면 조건이 자연히 생깁니다

C2. State Machine — "기억이 없다"가 아니라 출력 모양이 다른 것

기존"표본별 CASE라 래칭이 없습니다. 이름이 실제보다 큽니다"
매뉴얼맞지만 부족합니다. 레퍼런스의 출력은 표본별 값이 아니라 상태 점유마다 한 행이고 start_time과 time_interval(머문 시간 ms)을 냅니다 p370
왜 중요한가대표 용도가 그래서 두 가지입니다 — 커스텀 이벤트 생성과 절차 지연 측정. radio bearer 확립 시간이 time_interval로 바로 나옵니다. 래칭만 붙인다고 레퍼런스가 되지 않습니다
조치우리 노드의 정직한 이름은 Classifier. 진짜 State Machine은 별도 항목으로 세우고, 구간 출력을 요구사항에 넣습니다

정정

기존 정리는 "게이팅이 우리와 반대"라고 적었습니다. 더 정확히는 그들은 세 가지를 고를 수 있고, 우리는 그중 하나만 할 수 있습니다. 우리가 가진 것(outer join)은 정보를 가장 덜 버리는 선택이지만, "통화 중일 때만 보고 싶다"를 노드로 말할 방법이 없다는 것이 실제 격차입니다.

C7. Weight by — 두 축을 하나로 묶은 것이 잘못이었습니다 이 브리프의 자체 정정

기존"Weight by가 없는 것은 격차가 아니다" — "하지 않을 것" 표에 통째로 올려 놨습니다
매뉴얼Appendix 3, p477이 두 축을 명시적으로 나눕니다: "the duration can be in time or in distance … If the samples from the entire measurement route are to have equal weight and for instance the weighting effect of time spent at traffic lights is to be excluded, the samples should be weighted by distance." 같은 페이지가 시간 가중의 근거는 산수로 보여 줍니다 — 0/90초, 5/0.5초, 0/10초의 단순 평균 1.667 대 지속시간 가중 평균 0.025
SQL 층Appendix 6에 QSR_DISTANCE(p495) · QSR_TIME(p497) · SR_SAMPLE(p496)이 별개 프로시저로 있습니다. 입력 8개·반환 5개가 같고 가중 방식만 다릅니다
왜 틀렸나거리 가중의 근거는 표본 간격의 규칙성과 무관합니다. 그리고 1 Hz 균일 샘플에서 정차 편향은 오히려 가장 심합니다 — 신호 대기 중인 차는 초당 1표본을 꼬박 내면서 0 m를 이동합니다. 균일 샘플링은 시간 축을 해결하고 거리 축은 조금도 건드리지 않습니다
우리 상태거리 가중 집계가 어디에도 없습니다. 거리 비닝은 그 화면 안에서만 편향을 없애고, 통계·분포·비교 CDF·리포트는 전부 정차 편향을 안고 있습니다
조치"하지 않을 것"에서 거리 가중을 빼고 우선순위로 올립니다. 가중치는 거리 비닝이 이미 계산하는 대권거리 구간을 표본별 가중 열로 재사용하면 됩니다

C8. "셋 이상 테이블의 시간 상관은 SQL로 불가능" — 우리가 너무 세게 옮겼습니다 자체 정정

p332의 "with three or more tables the task becomes impossible"을 우리는 "SQL로 불가능"이라고 그대로 옮겨 적었습니다. 그런데 같은 매뉴얼 p480에 세 테이블을 시간으로 상관시키는 SQL 한 문장이 실려 있습니다 — REAL_FREEZE_FRAME을 두 번 부르고, 서브질의를 문자열로 넘기고, 첫 인자로 손으로 관리하는 캐시 순번(1, 2)을 줍니다.

정확한 표현: 평범한 조인으로는 안 되고 전용 스칼라와 수동 캐시 키가 필요합니다. 워크벤치는 불가능한 연산의 유일한 통로가 아니라 그 SQL의 인체공학 층입니다.

결론은 오히려 강해집니다. 우리 세로형 스키마에서 같은 상관은 평범한 키 조인입니다 — 그들이 전용 스칼라와 캐시 순번으로 치르는 비용을 우리는 치르지 않습니다.

C4. Lee's criteria를 근거로 댔지만 구현하지 않았습니다

기존"Distance binning ✅ 해소" — 그리고 커밋 메시지에 "the sampling convention drive testing has used since Lee"
매뉴얼Lee's criteria는 40λ입니다 p55. n78(3.5 GHz)에서 3.4 m, LTE 1800에서 6.7 m
우리 빈50 / 100 / 250 m — 두 자릿수 큽니다
조치거리 비닝 자체와 정차 편향 제거는 유효합니다. 그러나 "Lee's criteria"라는 이름은 뗍니다. 붙이려면 캐리어 주파수에서 40λ를 계산해 빈 크기로 제안해야 하고, 변환 함수는 이미 있습니다 (FieldToLabService.centreFreqMhz). 빈 좌표도 다릅니다 — 레퍼런스는 첫 이벤트, 우리는 빈 내 평균

C5. 드릴다운 좌측 탭은 스타일이 아니라 동시 유지 기능

기존"드릴다운 breadcrumb를 좌측 세로 탭 형태로 — 작음 · 순수 스타일"
매뉴얼"Each drill-down from the same chart will open a new tab … displayed on the left side of the window with the colors of the corresponding sectors" p88
실제 의미여러 원인을 동시에 열어 놓고 오가는 기능. RACH 실패와 핸드오버 실패를 나란히 비교하는 것이 이 도구의 사용법입니다. 우리는 Back to all categories 한 단계뿐이라 한 번에 하나
조치중간 규모의 기능 격차로 재분류했고, 2026-09-03에 닫았습니다 — 원인 탭이 여는 순서대로 쌓이고 탭 색은 파이 조각에서 가져옵니다. 진입 조작은 여전히 다릅니다 — 레퍼런스는 더블클릭, 우리는 한 번 클릭 (이 쪽은 우리가 낫다고 판단해 유지합니다)

C6. KPI Workbench는 그들의 스키마 한계 우회로이기도 합니다

셋 이상 테이블의 시간 상관이 "impossible" 하다 — 파라미터들이 관계가 정의되지 않은 별도 테이블에 있기 때문 p332

우리 sample_kpi는 세로형 단일 테이블이라 N개 KPI 상관이 같은 키의 조인입니다. 그들이 도구로 우회한 문제를 우리는 스키마로 이미 풀어 놨습니다.

실무적 함의가 큽니다: 우리 Combine 노드의 값어치는 그들만큼 크지 않습니다. 반대로 우리 워크벤치의 값어치는 전적으로 State Machine과 상관(Previous/Current/Next) 쪽에 있고 — 그 둘이 지금 우리에게 없거나 다릅니다. 개발 시간을 어디에 쓸지가 여기서 갈립니다.

C9. 워크벤치를 실제로 묶고 있는 것은 그래프의 모양 하나입니다 구조적 발견

매뉴얼 뒷부분(p396–504)까지 훑고 나서, 서로 달라 보이던 격차 넷이 같은 제약 하나에서 나온다는 것이 드러났습니다.

KpiGraph의 모든 CTE는 예외 없이 (session_id, seq, ts)를 키로 잡고, OUTPUT은 열 하나를 골라 sample_kpi에 실체화합니다. V8의 UNIQUE (output_kpi_name)이 그 계약을 스키마에 못박았습니다.

그래프 하나 = 표본당 한 행 × 출력 열 하나.
겉보기 격차실제 원인
이벤트를 캔버스에 못 올림 network_event는 (session_id, ts)이고 seq가 없습니다. 표본 격자 위의 행이 아니라 키가 맞지 않습니다
State Machine이 구간을 못 냄 구간 행은 start_time·time_interval을 갖는 다른 모양입니다. 표본당 한 행에 담을 곳이 없습니다
Nth Best · Group By 불가 행 수와 열 수를 바꾸는 노드들입니다. 매뉴얼은 이 부류를 "dynamic procedures … the actual result set is defined at runtime rather than fixed" 라 부릅니다 p501
지오메트리를 못 읽음 sample의 위경도·속도·서빙 PCI를 읽는 소스 노드가 없습니다. 이건 유일하게 모양 문제가 아니라 그냥 없는 것
그래서 우리가 공표한 우선순위 순서가 틀렸습니다

기존 순서는 ① 생성기 핸드오버 지연 → ② 진짜 State Machine → ③ Previous/Current/Next 였습니다. ②와 ③은 둘 다 위 제약에 걸립니다 — ②의 산출물인 구간 행은 실체화할 곳이 없고, ③의 대표 용도인 "드롭 직전의 값"은 드롭(이벤트)을 캔버스에 올릴 수 없어 성립하지 않습니다.

UC27이 그것을 그림으로 보여 줍니다 — 그 그래프의 마지막 노드가 Call dropped 이벤트와의 상관입니다. 우리는 거기서 시작조차 못 합니다. State Machine을 아무리 잘 만들어도 상관시킬 상대가 캔버스에 없습니다.

0번 항목이 새로 생깁니다 — 그래프가 낼 수 있는 두 번째 결과 모양을 정하는 결정. 반대로 SOURCE_SAMPLE(지오메트리 소스)은 이 결정과 무관합니다. 표본당 한 행, 열 하나 — 지금 모양에 정확히 맞고 값은 이미 sample에 있습니다. 지금 바로 할 수 있는 유일한 워크벤치 항목입니다.

3. 다음 우선순위

기준은 "이걸 안 하면 다음 구현을 잘못 만든다"의 정도입니다.

이 순위표가 쓰인 뒤 백로그 ①–⑧이 진행되어 0·1·2·6·7번이 닫혔습니다. 순서가 맞았는지가 여기서 드러납니다 — 0번 결정이 먼저 필요하다고 본 판단은 맞았고, 그 결정은 ⑥에서 세 번째 모양(발행하지 않는 미리보기)으로 내려졌습니다. 전체 대조는 Use Case 31개 대조표.

5 Previous / Current / Next Value 상관 노드중 C8. 2번 이후 — 상관시킬 이벤트가 있어야 의미가 생깁니다
6 거리 가중 통계 — 통계 · 분포 · CDF · 리포트중 C7. 1 Hz 균일이 없애 주지 못하는 유일한 편향 — ✅ ⑦에서 완료. 화면에 [Distance]·[Sample]이라는 이름으로 나옵니다. C7이 "두 축을 하나로 묶은 것이 잘못"이라고 정정한 그 두 축이 실제로 따로 골라집니다 — 가중 기준과 dB 평균 방식
7 폴리곤 영역 통계 — 지도에서 임의 영역을 그려 통계중 자산이 아니라 기능이었습니다. Polygon region p468 — ✅ ⑤에서 완료, 그리고 예상 밖의 절반이 하나 더 붙었습니다: 영역 안의 통계만이 아니라 통과 목록. 같은 사거리를 세 번 지났으면 한 장소의 세 번의 통과입니다
8 드릴다운 다중 탭중 C5. 재분류됨
9 Cell locator · 거리 빈 40λ 옵션 · 푸트프린트 3강 기준작음 UC21 · C4 · UC1. 데이터가 이미 있는 것들

4. 하지 않기로 한 것

격차표에 올라 있었지만 매뉴얼을 읽고 빼기로 한 항목들입니다. 빼는 근거가 "귀찮아서"가 아니라 우리 데이터 모델에서 의미가 없어서라는 점이 중요합니다.

항목왜 하지 않는가
Weight by time 시간 가중이 필요한 이유는 Nemo 파일이 값이 바뀔 때만 샘플을 만들기 때문입니다. 우리는 1 Hz 균일이라 가중 없는 평균이 맞습니다. 넣으면 의미 없는 컨트롤이 됩니다.
거리 가중은 이 표에서 뺐습니다 — C7 정정 참조
Time: Resample 같은 이유. 재표본화할 불규칙성이 없습니다
Sort 노드 정렬이 필요한 이유가 Union의 순서 파괴인데 우리는 Union이 없고 seq 키입니다. 아무 일도 하지 않는 버튼은 없느니만 못합니다
MapX · Spreadsheet grid · Info views · Network Parameters · Query clipboard MapInfo 자산 계열이거나, 우리가 다루지 않는 데이터 종류입니다. 범위 차이지 격차가 아닙니다
Indoor / IBWC maps 실내 측정은 우리 범위 밖입니다
드릴다운 더블클릭 진입 한 번 클릭이 낫다고 판단합니다. 파이 조각의 더블클릭은 발견하기 어려운 조작입니다. 고칠 것은 동시 유지 쪽입니다

5. 이 브리프가 남긴 방법론적 교훈 하나

우리가 노드 그래프를 설계하며 본 "스크린샷"은 이 매뉴얼 UC27의 완성 노드 그래프였습니다 — p425와 내용이 같고 크롭만 다릅니다. 정정 이 브리프의 첫 판에서는 "p405의 상태 흐름도"라고 적었는데, 근거가 파일 크기가 같다는 것뿐이었습니다. 이 매뉴얼에는 같은 크기의 그림이 최소 셋 있고, 픽셀로는 어느 것과도 맞지 않았습니다. 그림을 열어 보고서야 정체를 알았습니다.

구조 판독은 정확했습니다 — 노드 배치, 연결 방향, 상태 이름, 그리고 정렬 노드를 넣지 않기로 한 판단까지. 틀린 것은 전부 "화면에 보이지 않는 것"이었습니다 — State Machine의 출력 모양, Combine의 게이팅, Missing neighbour의 판정 방식, Lee's criteria의 수치.

노드가 화면 어디에 놓이는지는 그림에 있지만, 그 노드가 무엇을 출력하는지는 그림에 없습니다. 스크린샷 기반 분석의 한계가 정확히 거기였고, 이번 정정은 그 위에 하나를 더 얹습니다 — 메타데이터(크기·파일명) 일치를 내용 동일성의 근거로 쓰면 안 됩니다. 열어 보는 데 드는 비용이 훨씬 쌉니다.
