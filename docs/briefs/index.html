기존 툴 분석 브리프

Nemo Analyze 10.2 User Guide 기반 · 2026-09-01

지금까지 우리 UI 설계 근거는 스크린샷 판독과 마케팅용 Technical Overview였습니다. 메뉴 설명도, 사용자 절차도 없는 자료였습니다. 이번에 사용자 가이드 505페이지 전체가 들어오면서 처음으로 각 메뉴가 무엇을 하는지와 사용자가 어떤 순서로 조작하는지를 1차 자료로 확인할 수 있게 됐습니다.

이 브리프는 그 결과입니다. 각 문서는 세 부분으로 구성됩니다 — 메뉴 설명(원문 근거와 그림), 유저 시나리오(매뉴얼의 Use Case), 그리고 우리 구현에는 어떻게 반영됐는가.

브리프

문서다루는 것
① Workspace와 데이터 뷰 좌측 도크 3단 구조, 파라미터에서 나오는 질의 진입점들, 뷰 종류 전체. 우리 화면의 직접 대응물
② 분석과 드릴다운 문제 조사 파이 → 사례 그리드 → 그 순간. 영역·거리 비닝, 셀 푸트프린트, 파일럿 오염, Cell locator
③ KPI Workbench 노드 그래프 KPI 빌더의 요소 전체 명세와 UC27 실전 예제. 우리와 가장 크게 어긋난 곳
④ 워크북과 리포트 워크북·페이지·데이터뷰 3층 구조, 리포트 템플릿 3종
⑤ 판정 요약 매뉴얼이 우리 기존 판단을 확인한 것과 뒤집은 것, 그리고 다음 우선순위
⑥ 메뉴 바와 질의 API 메뉴 8개·항목 77개 전체, 단축키, 그리고 스칼라 함수 46 + 프로시저 16. 원래 질문이었던 "각 메뉴에 대한 자세한 설명"이 있는 곳

대조표

문서다루는 것
Use Case 31개 대조표 매뉴얼의 유즈케이스 31개 전부를 한 표에서 우리 구현과 맞춰 봅니다. 브리프 여섯 편에 흩어져 있던 대응 관계를 한 자리로 모은 것 — 흩어져 있는 동안은 8개가 어느 문서에도 없었고, 그중 셋은 이미 구현돼 있었습니다. 브리프의 "남은 일" 표가 판단의 기록이라면, 이 표는 현재 상태의 기록입니다
⑦ Use Case 31개 상세
Markdown: use-cases.md		 매뉴얼이 각 유즈케이스에서 무엇을 하라고 하는지 — 목적·절차·원문 인용·그림 — 를 장 순서대로. 항목마다 근거 등급을 붙여 원문이 남아 있는 것과 제목만 남은 것을 가릅니다. 대조표가 우리 상태라면 이쪽은 레퍼런스의 내용입니다. 2026-09-02 원문 전사판 — 유즈케이스마다 필요한 입력 데이터와 우리 데이터 모델에 있는지를 명시
⑧ Use Case 요약표 31개를 설명 · 전제 · 입력 · 출력 네 열로 한 줄씩. 우리 구현과의 비교 없이 매뉴얼 내용만 간결하게 — 회의에서 훑어보는 용도
⑨ 입력 기준 분류와 사용자 시나리오 31개를 장·절이 아니라 필요한 입력 데이터로 다시 묶은 9개 그룹과, 그 묶음을 합쳐 업무의 처음부터 끝까지를 푼 시나리오 7편(드롭콜 원인 · 사이트 DB 검증 · 전후 비교 · 음성 감사 · 처리율 심층 · 5G 빔 · 자동 리포팅). 이 작업이 설계 과정의 어느 단계에 놓이는지와, 우리 E2E 검증 여정 S1–S13과의 대응표 포함

한 장 요약

매뉴얼을 읽고 바뀐 것은 크게 넷입니다.

항목기존 판단매뉴얼 확인 후
State Machine "래칭이 없어 이름이 과하다" 더 큼 기억뿐 아니라 출력 모양이 다름. 레퍼런스는 상태 점유마다 한 행 + time_interval. 우리 것은 분류기
Missing neighbour "설정된 이웃 목록이 없어 원천 불가" 틀림 레퍼런스는 측정값만으로 판정. 막고 있던 건 스키마가 아니라 핸드오버 지연을 모델링하지 않는 생성기
Lee's criteria "거리 비닝으로 해소" 이름값 미달 실제 기준은 40λ — n78에서 3.4 m. 우리 최소 빈은 50 m
드릴다운 좌측 탭 "작음 · 순수 스타일" 재분류 여러 원인을 동시에 열어 두는 기능. 중간 규모

반대로 확인된 것도 있습니다. 노드 그래프의 구조 판독은 정확했고, 정렬 노드를 넣지 않은 판단은 매뉴얼이 그 이유까지 확인해 줬습니다 (⑤).

2차 통과에서 바뀐 것 p396–504 정밀 조사

매뉴얼 뒷부분(UC27 전체 · ch.12 · 메뉴 장 · 부록 5·6·7)을 따로 훑으면서 우리 자신의 판단 셋을 정정했습니다. 셋 다 "닫아 놓은 결정"이었다는 점이 공통점입니다 — 다시 들여다볼 이유가 없어 위험한 종류입니다.

항목정정 전정정 후
Weight by "만들지 않음" — 통째로 절반 틀림 거리 가중은 격차입니다. 근거가 표본 간격과 무관하고(p477), 1 Hz 균일에서 정차 편향은 오히려 최악
"SQL로 불가능" 셋 이상 테이블 시간 상관은 SQL로 불가능 과했음 p480에 세 테이블을 잇는 SQL 한 문장이 있습니다. 평범한 조인으로 안 될 뿐
푸트프린트 "빔폭·반경 미기록이라 설계 커버리지 불가" 엉뚱한 입력 레퍼런스는 안테나 높이·틸트로 추정합니다(p459). nullable 두 열이면 열립니다
Polygons "MapInfo 자산 — 범위 밖" 기능을 놓침 Polygon region은 "run statistics over that area"(p468). 자산과 기능을 갈랐어야
우선순위 순서 ① 생성기 → ② State Machine → ③ 상관 노드 재배열 ②③이 같은 제약 하나에 걸립니다 — 그래프가 표본당 한 행 × 열 하나로 고정. 0번(결정)이 앞에 옵니다

그리고 ①에서 스크린샷의 정체를 다시 고쳤습니다 — 첫 판에서 크기가 같다는 이유로 "p405 상태 흐름도"라고 적었는데, 같은 크기 그림이 셋이라 치수 일치는 식별이 아니었습니다. 열어 보니 완성 노드 그래프였고, 그래서 결론이 반대로 바뀝니다 — 우리는 완성본을 보고 설계한 것이 맞습니다.
